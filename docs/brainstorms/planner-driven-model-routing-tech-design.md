**Overlaps surfaced:**

- `design:routing-envelope-v1` is the direct predecessor: its optional scalar rung and `Rung == 0` absence sentinel are incompatible with the required plan/v2 assessment/profile contract, so a successor must supersede it rather than edit it.
- `design:plan-new-v1` freezes plan/v1, its generated JSON, and the projection/dialect boundary. The new basis requires a versioned successor contract and lossless transport; the frozen PRD also requires a typed `plan-new` amendment before this design can be authored.
- `design:implement-now` freezes `Task.Rung`, `AgentRuntime.TierMap`, and rung-clamped implementation launches. Those decisions are replaced by semantic profile resolution for a preselected harness, while backend choice, fresh-process isolation, verification, and the five-port Worker remain valid.
- Mainline after PR #709 adds an explicit backend-selection cascade and default review-harness inheritance that the frozen `implement-now` design does not describe. `implement-now-v2` must carry that cascade forward unchanged, then call semantic resolution only after the harness and role are fixed.
- `design:impl-review-v1` stays authoritative for reviewer independence, reviewed-revision binding, and proposal persistence. This feature extends its invocation with the monotone assurance join and an independent review-role native resolution; it must not create a second proposal-risk classifier.
- `design:feature-implementation-drive` owns the feature's local/remote owner domain and fencing epoch above `implement-now`; it is not a model-routing owner. A successor to `implement-now` creates a currency audit for this dependent design, but a `stale-builds-on` result alone is not a contradiction and does not justify superseding FeatureDrive.
- `design:local-work-tracker-v2` owns the tracker port and conformance. It is extended so both GitHub and Carina round-trip the frozen demand; no tracker may reinterpret or reconstruct the fields.
- `design:merge-lane-v1` remains the sole classifier of actual proposal risk and is consumed read-only. Its skip/standard/deep semantics are not re-decided.
- `design:pipeline-measurement-v2` may supply already-exposed usage measurements, but its gitignored runtime record is not the FR-21 evidence source; routing decision/outcome evidence needs its own committed immutable class.
- No live design Serves `prd:planner-driven-model-routing`; the feature is not covered. The work is a coordinated successor/extension set over existing frozen contracts, not greenfield.

## Decisions

### D-1 — evolve the existing products; version contracts and decision records only

- **Question**: DQ-1 — should planner-driven routing create new planning/execution products, or update the existing `plan-new` and `/implement-now` surfaces; and what do the proposed v2 labels mean?
- **Answer**: Update the existing `plan-new`, WorkTracker, `/implement-now`, harness-adapter, and impl-review product/code paths. Create no parallel planner or executor. `plan/v2` is only the closed data-contract version needed to add mandatory assessment/profile fields while frozen plan/v1 remains readable through translation. The current `implement-now` CLI and implementation are changed in place; because its merged technical design is immutable and its binding `TierMap(rung)` decision becomes false, a new successor decision record must supersede that design, but the successor need not present itself as a second or “v2” runtime product. Existing `plan-new`, `implement-now`, and `impl-review` PRD contracts evolve through their required typed amendments.
- **Reasoning**: This preserves product continuity and the operator's “update the existing one” intent while respecting the repository's two distinct evolution mechanisms: row-granular amendments for PRD ledgers and whole-document supersession for contradicted frozen technical designs. It also makes ALT-5's five documents decision boundaries, not five replacement products.
- **Anchor**: 2026-07-26 · “sounds good,” confirming the proposed interpretation of “let's update the existing one”
- **Status**: live

### D-2 — declarative derivation policy; plangate authors the frozen profile

- **Question**: DQ-2 — should execution-demand derivation be code-native or declarative, and should the planner hand-copy the derived profile or should plangate generate the checked frozen capsule?
- **Answer**: Adopt ALT-9 and its exact candidate table/promotions. The planner authors the closed `model` assessment, one or more resolvable assessment-evidence citations, and any evidence-backed assurance raise; `no_inference` is a separate closed arm and remains distinct from `Mechanical`. One immutable declarative `execution-demand-policy/v1` artifact owns the ladders, 18 component-floor rows, and six named monotone promotions. Plangate alone applies max-of-floors, promotions, the optional assurance raise, and the critical-assurance closure, then freezes the raw judgment, policy version+digest, matched promotion IDs, raise provenance, and final profile as one canonical capsule. Fold, verify, projection, CI, and claim-time integrity use the same Go evaluator and exact pinned policy.
- **Reasoning**: This gives every value one author: the planner owns judgment, reviewed policy data owns the mapping, and deterministic code owns arithmetic. It preserves both raw and derived frozen artifacts required by the PRD without manufacturing planner-versus-gate mismatches, keeps native model identifiers out of plans, and makes historical policy replay exact.
- **Anchor**: 2026-07-26 · “yes” to adopting ALT-9 and its proposed floor/promotion table
- **Status**: live

### D-3 — role-qualified native catalogs with one resolver and generated total proof

- **Question**: DQ-3 — should each harness hand-author every semantic-demand cell, or define each role-qualified native profile once and mechanically project the complete routing matrix?
- **Answer**: Adopt ALT-11. After the upstream selector fixes the harness and the caller fixes `implementation|review`, one pure shared resolver filters that harness-role catalog by four-component dominance and selects the unique lowest reviewed `cost_rank`. It returns typed `exact`, `promoted` with named overprovided components, or an explicitly declared `unsupported`; it cannot inspect or switch harnesses. Each adapter owns separate implementation and review catalogs with typed model/effort, stable profile identities, bound qualification evidence, explicit unsupported cells, and a declared strongest fallback. A generated byte-verified matrix exhaustively covers every registered harness × both roles × every profile derivable under D-2. Operator-ratified repository overrides replace a complete compatible harness-role catalog, never field-merge or inject launch arguments.
- **Reasoning**: The catalog gives volatile native model facts one author, while the generated matrix provides the explicit totality and least-cost proof of a hand-written cell table without duplicating roster data. Role-specific evidence prevents review from inheriting implementation capacity; typed launch values preserve adapter-safe argv construction; policy digests and qualification artifacts make every decision replayable and invalidatable.
- **Anchor**: 2026-07-26 · “sounds good” to adopting ALT-11
- **Status**: live

### D-4 — sealed self-contained transport; frozen plan remains authority

- **Question**: DQ-4 — should execution demand travel as tracker-authoritative capsule bytes, as a compact reference reconstructed from the frozen plan, or as a complete transported capsule whose authority is verified against that plan?
- **Answer**: Adopt ALT-14. Plangate writes exactly one closed canonical `execution-demand-capsule/v1` marker into the common GitHub/Carina task body before the task becomes routable. The marker carries the complete D-2 capsule plus exact plan/task identities and content fingerprints; one shared codec decodes it into typed `Task.ExecutionDemand`, and adapters never map or infer fields. The tracker is a self-contained carrier/cache, not authority: projection readback, pre-claim validation, and review compare the capsule to the exact frozen plan task on trusted mainline. Missing, duplicate, malformed, stale, copied, truncated, or mismatched data fails before claim or invocation. Normal review receives the verified Task; proposal state persists the same capsule identity/digest so restarted or orphan review can independently re-verify it before joining assurance and resolving `role=review`.
- **Reasoning**: Reference-only transport gives the strongest single authority but cannot directly prove every assessment/profile field survived both media and makes tasks dependent on reconstruction. Capsule-only transport proves round-trip completeness but lets mutable tracker content become a second authority because an editor can replace both payload and digest. The hybrid keeps lossless, medium-identical, self-contained work while one bounded frozen-plan comparison detects both accidental loss and deliberate tracker substitution. Existing projection ordering already permits verification before routing, and the existing Task/review seam carries the typed result without a second interpretation path.
- **Anchor**: 2026-07-26 · “yes” to adopting ALT-14
- **Status**: live

### D-5 — remove `no_inference` from planner-driven `/implement-now` routing

- **Question**: Should this feature add a new deterministic execution path for `no_inference`, treat such entries as non-executable metadata, or remove the option because `/implement-now` work is model-backed by definition?
- **Answer**: Remove `no_inference` from this feature and from the plan/v2 execution-demand contract it introduces. Every executable task projected to `/implement-now` must carry the complete six-axis assessment and derived four-component profile and must enter harness-native resolution. Deterministic commands remain inside existing gates, generators, and tooling; they are not modeled as `/implement-now` work tasks. A future deterministic recipe/runner would be a separate explicitly scoped product capability with its own security and verification contract, not an empty arm in model routing.
- **Reasoning**: The current Worker has exactly one work-producing path—launching an AgentRuntime from a natural-language charter—and the merged basis supplies no deterministic recipe or non-agent executor. Retaining `no_inference` would promise an execution mode that cannot execute and would create an undefined review path. Removing it keeps this feature aligned with its actual job: choosing appropriate model capacity and effort for agent-backed implementation and review. It also removes P-1's deterministic-review contradiction rather than designing around it.
- **Anchor**: 2026-07-26 · “yep, let's remove the no_inference option”
- **Status**: live amendment direction — not effective until `prd:planner-driven-model-routing` is amended and merged

## Alternatives

### ALT-1 — one vertical successor

- **Shape**: One `planner-driven-model-routing-v1` document carries the complete plan-to-outcome protocol. It supersedes `routing-envelope-v1`, `plan-new-v1`, and `implement-now`, carries their still-valid decisions forward, and builds on `impl-review-v1`, `local-work-tracker-v2`, `merge-lane-v1`, and `pipeline-measurement-v2`.
- **Trade-offs**: One cross-path contract and one cutover owner minimize coordination and version drift. The cost is one enormous supersession boundary combining plan semantics, policy, two runtime roles, evidence, and production controls; revising any one reopens all of them.
- **Principles**: AP-10/AP-11 and AP-21 are strong (one protocol and predicate); AP-20 and RW-5 are strained because several independently revisable questions share one document; RW-6 requires an explicit direct-cutover deviation with equivalent pre-release evidence.
- **Incidents**: I1 satisfied by the merged basis and prerequisite amendments; I4 makes complete carried-forward `Serves` coverage difficult and load-bearing; I5 requires one hermetic resolver/conformance path despite the document's breadth.
- **Verdict**: rejected by rerun — even before adding the newly explicit selector and FeatureDrive boundaries, the document combines unrelated reasons to change.
- **From**: DQ-1 · panel

### ALT-2 — two vertical halves

- **Shape**: `execution-demand-contract-v1` supersedes `plan-new-v1` + `routing-envelope-v1` and owns plan/v2, derivation, transport, and v1 translation. `routed-execution-v1` supersedes `implement-now`, builds on `impl-review-v1` + `merge-lane-v1`, and owns native policy, both roles, evidence, fallback, and cutover.
- **Trade-offs**: Cleanly separates stable vendor-neutral demand from volatile native execution and matches the PRD's broad Phase A/Phase B split. The runtime half still bundles policy, evidence retention, implementation integration, and independent review—four different reasons to change.
- **Principles**: AP-6/AP-13/AP-21 are strong at the demand boundary; AP-20/RW-5 improve over ALT-1 but remain strained in the runtime half; AP-1/AP-3 rely on careful adapter conformance within that broad document.
- **Incidents**: I1 requires all three PRD amendments first; I3 constrains the broad policy/cutover surface to closed parsing; I4 applies to both halves' union coverage; I5 requires the same predicate at desk, CI, and dogfood.
- **Verdict**: candidate but not recommended — still credible, but its runtime half would conflate the upstream selection cascade, native policy, evidence, implementation, and review evolution.
- **From**: DQ-1 · panel

### ALT-3 — four-design routing spine

- **Shape**: `plan-new-v2` supersedes `plan-new-v1` + `routing-envelope-v1`; `execution-routing-substrate-v1` owns native policy, resolver, conformance, immutable evidence, invalidation, activation, and kill switch; `implement-now-v2` supersedes `implement-now`; additive `impl-review-routing-v1` builds on `impl-review-v1` + `merge-lane-v1`.
- **Trade-offs**: Planner, shared substrate, implementation, and review can evolve independently, with one fewer integration contract than ALT-4. Policy/qualification changes and evidence-schema/invalidation changes nevertheless share a supersession boundary even though their operational cadences differ.
- **Principles**: AP-1/AP-3, AP-6, AP-20/AP-21, AP-24, and RW-4/RW-5 are substantially honored; AP-28 is coupled to the policy substrate rather than independently owned.
- **Incidents**: I1 orders amendments before designs; I2 requires bottom-up landing and ancestry verification; I3 closes policy and activation parsing; I4 requires per-design plus union `Serves`; I5 binds one hermetic conformance/release predicate.
- **Verdict**: hybridized into ALT-5 — the four primary ownership seams survive, but the rerun keeps policy and retained evidence independently revisable and fixes selector ownership upstream.
- **From**: DQ-1 · panel

### ALT-4 — five seam-owned designs

- **Shape**: ALT-3 split further: `plan-new-v2`; `native-routing-policy-v1` for dominance, least-cost qualification, adapter catalogs, overrides, conformance, activation, and fallback; `routing-evidence-v1` for attempt identity, committed decision/outcome records, joins, invalidation, and audit; `implement-now-v2`; additive `impl-review-routing-v1`.
- **Trade-offs**: Each design answers one independently revisable question; native roster/policy work cannot disturb evidence retention, and review cannot disturb implementation. It costs five reviews, explicit interfaces, a dependency order, and a union coverage check; two successors must carry forward the large plan/executor contracts.
- **Principles**: AP-1/AP-3, AP-6, AP-10/AP-11, AP-20/AP-21, AP-24, AP-28, RW-4, and RW-5 are strongest here; RW-6 is honored in intent through earned pre-release evidence while its shadow/canary mechanism is explicitly displaced by the operator's direct-cutover requirement.
- **Incidents**: I1 fixes amendments-first; I2 fixes landing verification; I3 fixes closed policy/activation; I4 fixes exhaustive per-design and union `Serves`; I5 fixes one hermetic predicate and prevents measurements becoming a second gate.
- **Verdict**: hybridized into ALT-5 — the five-way partition survives, but the demand design's successor scope and the selector/resolver boundary are now stated more narrowly.
- **From**: DQ-1 · panel

### ALT-5 — five seam-owned decisions, updating the existing products

- **Shape**: All implementation lands in the existing `plan-new`, WorkTracker, `/implement-now`, adapter, and impl-review product/code paths; there is no parallel planner or executor. The five independently revisable decisions are: (1) `execution-demand-contract-v1` supersedes `routing-envelope-v1`, builds on `plan-new-v1` + `local-work-tracker-v2`, and owns the new `plan/v2` assessment/profile schema, derivation, validation, transport, and v1 translation; (2) `native-routing-policy-v1` owns the closed harness×role catalogs, qualification, dominance, least-cost resolution, promotion/unsupported results, activation, and strongest-profile fallback; (3) `routing-evidence-v1` owns immutable decision/outcome/invalidation records and joins; (4) an `implement-now` successor design carries PR #709's selector cascade forward unchanged and replaces `TierMap` only after the harness is selected; (5) additive `impl-review-routing-v1` builds on `impl-review-v1` + `merge-lane-v1`, owns the monotone assurance join, and resolves `role=review` independently on the inherited-or-overridden review harness. `plan/v2` is a data-contract version; an `implement-now` successor is a decision-record generation, not a second runtime surface.
- **Boundary invariant**: `FeatureDrive owner domain → task route | repository default | declared ambient harness → resolve(selected harness, role, semantic demand) → adapter launch`. The native resolver cannot choose local/remote ownership, inspect selector precedence, infer installed CLIs, or fall back to another harness. Generated harness skill views may declare ambient identity but never embed native model policy.
- **Supersession audit**: `plan-new-v1` remains true as the frozen plan/v1 contract; the new demand design is additive at plan/v2 while superseding only the scalar routing envelope. `implement-now` must be superseded because `TierMap(rung)` becomes false. `impl-review-v1` and FeatureDrive receive explicit currency audits, but remain live unless an actual binding contradiction is found; their reviewer-isolation and owner-domain statements are preserved.
- **Trade-offs**: Five reviews and explicit interfaces cost more coordination than ALT-2, but planner demand, volatile native rosters, retained evidence, implementation integration, and review integration each change for different reasons. This shape also avoids converting dependency freshness warnings into unnecessary whole-document successors.
- **Principles**: AP-1/AP-3 keep the resolver contract common and native policy adapter-owned; AP-6/AP-8/AP-24 close and authorize policy data; AP-10/AP-11/AP-21 preserve one derivation and one satisfying predicate; AP-17 fails before claim/invocation; AP-20 limits blast radius; AP-28 gives retained evidence its own data class; RW-4/RW-5/RW-6 govern substrate-first direct activation.
- **Incidents**: I1 fixes amendments before design; I2 fixes train ancestry verification; I3 fixes explicit ambient/unknown-policy failure; I4 fixes carried-forward and union `Serves`; I5 fixes the same conformance predicate across desk, CI, dogfood, and activation.
- **Verdict**: selected by D-1 — PR #709 strengthens rather than collapses the partition: harness selection is an established upstream contract, while native routing remains independently harness-qualified policy.
- **From**: DQ-1 · rerun panel after PR #709

### ALT-6 — full dependent-successor wave

- **Shape**: `plan-new-v2` supersedes `plan-new-v1` + `routing-envelope-v1`; a combined native-policy/evidence design owns resolution; `implement-now-v2` supersedes `implement-now`; `impl-review-v2` supersedes `impl-review-v1`; and `feature-implementation-drive-v2` supersedes FeatureDrive so every direct or transitive `Builds-on` reference names the newest design generation.
- **Trade-offs**: All dependency headers become current in one coordinated wave and the number of new routing substrates falls by one. In exchange, unchanged plan/v1, reviewer-isolation, feature ownership, reconciliation, and fencing contracts are reopened solely because their dependencies advanced; the landing train, carried-forward `Serves`, and regression proof grow substantially.
- **Principles**: AP-10's single coherent path is visually strong, but AP-20 and RW-5 are strained by broad successor blast radius; AP-28 is weakened by coupling evidence evolution back to model policy. A `stale-builds-on` audit is treated as a supersession trigger even though the design conventions require a successor only when a binding statement becomes false.
- **Incidents**: I2 and I4 become especially load-bearing because a large successor train must prove both ancestry and exhaustive carried-forward coverage; I5 requires broad unchanged-subsystem regression evidence.
- **Verdict**: not recommended — no contradiction has yet been shown in `impl-review-v1` or FeatureDrive. Currency must be audited, but dependency freshness alone is insufficient grounds for supersession.
- **From**: DQ-1 · rerun panel after PR #709

### ALT-7 — code-native policy with a planner-authored checked profile

- **Shape**: Plan/v2 uses a closed `execution_demand` tagged union. `mode=no_inference` forbids assessment/profile/policy/raise fields. `mode=model` requires all six assessment values, at least one resolvable assessment-evidence citation, a policy version, all four planner-authored profile values, the matched promotion IDs, and an optional evidence-backed assurance raise. The 18 floor rows and named promotion predicates live as version-keyed Go data; old versions remain compiled for frozen plans. Plangate calls the same evaluator to recompute and compare every supplied value before freeze.
