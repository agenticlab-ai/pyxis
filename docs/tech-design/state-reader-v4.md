## 1. Problem

The factory can write to its media — open proposals, post comments — but cannot see them: no port answers "which of these proposals landed? which got comments? which failed which required check?" (basis §2.1; the port gap is `internal/executor/port/` read verbatim in design-brainstorm:self-drive-wake-tech-design#F-4). Every consumer that needs the answer today either cannot exist (the wake loop, the status verb) or would invent its own medium client (the drift path). Two constraints make *this* the cheapest moment: the read shape must be settled with both media in view before any consumer bends it around one (the basis's D-3 lesson — today's gap came from exactly that), and the read must be budget-safe by construction because it will run every few seconds for hours (basis NFR-1, FR-8).

Budget-safety has a second half this design's predecessor got wrong, and the correction is why v3 exists. A throttle that blocks writes is a *safety* mechanism only where the state it reads carries information. v2 contracted one recovery rule — "corrupt, unreadable, or missing ⇒ start conservative" — for three states, and the implementation followed it faithfully into a self-inflicted outage: every ephemeral driver checkout starts without a bucket, so every ephemeral driver charged itself a full hour-window before its first write, for spend that never happened (incident:I7). The bucket also lived inside the driver's own checkout — a location whose lifetime is unrelated to the window the platform meters — so it was never the machine-shared thing its own contract described.

v3 repaired that and introduced a second version of the same mistake, which is why v4 exists. Having keyed the ledger to (host, identity), v3 had to say what happens when the identity cannot be read, and answered "key by **medium host alone**, the coarser direction this rule already mandates". That is safe-sounding and wrong: a host-keyed ledger only unresolved writers touch is a *sibling* of the identity ledger, not a bound on it. Identity lookup is retried rather than memoized after a failure — deliberately, so a transient blip cannot pin a long-lived process to the coarse key — so a resolved and an unresolved process coexist routinely, and as siblings the pair spends two full windows against what may be one quota. That is *under*-throttling, the one direction v3's own rule forbids. **"Coarser" is a claim about containment**, and a design that does not say which ledgers charge which has not made it.

Repairing it changed the persistence topology, so the requirements moved first: prd:self-drive-wake amendments **002** (the host umbrella, the cutover barrier, the deferral event's semantics) and **003** (the downgrade drain) are merged, and this document carries them into the design layer.

## 2. Decision

**Decision:** One new **reader port** — a single batched state read — added as a new file beside the existing executor ports, implemented by the existing GitHub and Carina adapter packages, and bound by a conformance kit. Per proposal the read returns: **landing state as the medium's claim** (open · landed · closed-unlanded · unknown) carrying the medium-reported landed revision id; **per-context check states** compared against the medium's required set, never an aggregate rollup alone; and **comments newer than a caller-held cursor** across the medium's proposal-discussion surfaces. All read failures resolve to a typed **unknown** — never an error masquerading as absence, never a default. On metered media, every content-*write* is admitted by a shared, flock-guarded budget that blocks callers (context-aware) instead of ever letting a platform rate-limit response occur. That budget is a **ledger pair** in the machine's state directory — the writing identity's ledger plus a **host umbrella that every identity ledger also charges** — guarded by a durable **cutover marker** per (machine, medium host): a resolved write charges both ledgers, an unresolved write charges the umbrella alone, and an absent ledger is free only under a valid marker. Existing port interfaces are untouched; the existing per-proposal `Checks` read delegates to the new implementation internally. (design-brainstorm:self-drive-wake-tech-design#D-2, #D-6, #D-8; ALT-5)

The reasoning, stated once. The port is a platform contract (AP-3) whose granularity must be set by the *metered* medium — per-item reads are free on Carina and an unfixable N+1 on GitHub (basis §2.4, measured), so the interface is batch-shaped with a declared round-trip bound the kit asserts. Landing is deliberately a *claim*: a medium's "merged" certifies the medium's object, never the mainline (AP-26; incident I2), so the reader carries what goal-object verification needs and asserts nothing it cannot know.

The budget's shape follows from one idea taken seriously: **a coarser bound is safe only when it contains the finer ones.** A coarse ledger standing *beside* them is not a fallback, it is a second full window — which is what v3's fallback clause specified and what shipped. Everything else follows. The umbrella is charged by every write, so it genuinely bounds the host (DINV-9). Admission is atomic over whatever set a write charges, so no *capacity decision* is taken for a write that is not admitted (DINV-11). That is a statement about the decision, not about bytes: when the identity ledger's persistence fails after the umbrella is durable, the umbrella's charge is deliberately **retained** and the content write is not sent — spend recorded for a write that never happened, in the over-throttling direction, because the alternative is a compensating write that can fail in turn (DINV-12). Fail-closed is scoped to where failure hides something (AP-17): unreadable state may encode spend the reader cannot see and is paid for, while absent state on a cut-over host hides nothing and costs nothing — but *absence itself* is only informative once a barrier has been paid, which is what the marker records (DINV-6, DINV-13). And because the platform's counter does not move when pyxis changes where it records things, both directions of a version change are gated.

*(v4 supersedes state-reader-v3 for one reason: v3's §3.8 fallback clause could not be built as written. "When the identity cannot be resolved the bucket keys by **medium host alone**" produces a *sibling* of the identity ledger rather than a bound on it, and since identity lookup is retried rather than memoized after a failure, a resolved and an unresolved process coexist routinely and spend two full windows against what may be a single quota — under-throttling, the one direction v3's own rule forbids. ## 3. The design

### 3.1 The reader port

**Decision:** One interface, one method, in a new file in the executor's port package — consumer-side, per the hexagon (ports are declared by what the engine needs).

```go
// port/statereader.go (new file; nothing existing edited)
type ProposalStateReader interface {
    // States returns one ProposalState per requested ref — always all of
    // them, in order; a proposal the medium cannot answer for is returned
    // as StateUnknown with a typed reason, never omitted (DINV-1).
    States(ctx context.Context, refs []ProposalRef, since Cursor) ([]ProposalState, error)
}
```

- **`ProposalRef`** — the medium-neutral proposal identity (number + repo scope), the same identity `CodeHost.OpenProposal` returns today.
- **`ProposalState`** — closed struct: `Landing` (enum `open · landed · closed-unlanded · unknown` + `LandedRevision string` — the medium's claimed landed commit/record id, empty only when not landed) · `Checks []CheckContext` (`{Name, State}` per context, plus `RequiredMissing []string` — required contexts with no run observed) · `Comments []Comment` (author, created-at, surface kind, body ref) · `Unknown *UnknownReason` (typed enum: `rate-limited · offline · parse-defect · timeout`).
- **`Cursor`** — caller-held opaque per-surface positions (the reader is stateless, DINV-7); `since` filters comments only.
- **Comment surfaces** (the basis FR-1's enumerated classes, mapped per medium in §3.6/§3.7): discussion comments, inline review comments, review summaries.
- **The top-level `error`** is **read-side only**: context cancellation, and transport failures that defeat the read itself. It carries no budget or ledger condition, because `States` performs no content write and touches no ledger — the write budget's substrate errors (state directory uncreatable, a lock unopenable, a replacement unwritable) and DINV-12's failed-persistence branch are returned by the **content-write operation that incurs them**, never surfaced through a read. Partial medium failures are per-proposal `Unknown`; the error return never smuggles state (DINV-2).
- **Delegation:** the existing `CodeHost.Checks(one)` implementation becomes a call through the same per-context derivation this port defines (adapter-internal; no interface change) — one implementation of "is this green?" (AP-11).

### 3.2 Boundaries and non-goals

- **Not solved here** — when and how often the reader is called (wake-watch-v2's cadence loop); what a consumer does with a landed claim (its own contract's goal-object verification); rendering (the status verb).
- **Owned by a future design** — wake-channel-v1's re-plumb of its per-goal probes onto this port (its own evolution — design-brainstorm:self-drive-wake-tech-design#O-1); further medium adapters (GitLab et al.) by following the kit (AP-3); any mechanism that *learns* a platform's real limit scope rather than assuming the coarser one (§3.8's key is fixed by what the platform documents, not by probing); and the **downgrade drain's enforcement**, which prd:self-drive-wake/UB-8 places on the operator procedure and the release gate — this design owes it only the marker semantics that make it possible (§3.8, A-17) and deliberately does not carry those anchors in `Serves`.
- **Implementation must not infer** — that `landed` implies mainline ancestry (it is the medium's claim — DINV-3); that an aggregate rollup may substitute for contexts (DINV-4); that a failed read may default to any definite state (DINV-2); that the reader may cache or persist medium content (DINV-7); that a missing ledger is evidence of anything (DINV-6); **that a coarser fallback may stand *beside* the ledgers it bounds rather than being charged by every write they take** (DINV-9) — this is the inference that shipped a quota split and the reason this document supersedes v3; that admission always spans two ledgers (DINV-11 — the unresolved path charges one); that ordering two `write()` calls orders their durability (DINV-12).
- **Must remain unchanged** — every existing port interface and its adapters' external behavior (basis NR-2: existing write paths keep working under the budget; NR-1's executor semantics are untouched by construction — this design adds a port, changes no executor code path).

### 3.3 Invariants

- **DINV-1** — A batch read answers **every** requested ref exactly once; a proposal the medium cannot answer for is a typed `unknown`, never an omission, an empty struct, or a healthy-looking zero value (the swallowed-evidence class, research §3.2).
- **DINV-2** — No consumer-visible state transition derives from a failed read: `rate-limited/offline/parse-defect/timeout` all resolve to `unknown — retry later`; the top-level error carries no per-proposal state.
- **DINV-3** — Landing state is the **medium's claim**: every `landed` carries the medium-reported landed revision id, and the reader asserts nothing about mainline ancestry — goal-object verification is the consumer's act (AP-26; basis FR-13).
- **DINV-4** — Check state derives from the per-context set compared against the required set; an aggregate rollup alone never yields green, and a required context with no observed run reports as `RequiredMissing` ⇒ not-green (basis FR-3).
- **DINV-5** — On a metered medium, one batch completes within the adapter's declared round-trip bound, asserted by the conformance kit (basis FR-2).
- **DINV-6** — Every content-write on a metered medium is admitted by the shared budget before sending; saturation blocks the caller context-aware — a platform rate-limit response reaching a caller is a defect, not weather. Recovery is decided by what a ledger's state can hide, **gated on a valid cutover marker for that host**: with the marker present and readable, **absent ⇒ start empty** (the barrier is paid, no prior holder existed, so no unobserved spend exists to protect against, and nothing is persisted before the grant); **present but unreadable ⇒ start conservative** (both windows assumed spent, refilling on the clock — the bytes may encode spend the reader cannot see); **marker absent or unreadable ⇒ start conservative regardless of the ledgers**, because an un-cut-over host is exactly what an absent ledger looks like and the two cannot be told apart without the marker. Throttle state is never partitioned finer than the platform documents its limit; an undocumented scope is assumed coarser, never narrower (prd:self-drive-wake §5.4; incident:I7).
- **DINV-7** — The reader is stateless: cursors are caller-held and no medium content is persisted. Its state is the two **ephemeral** ledgers — the identity ledger and its host umbrella — plus the **durable cutover marker** per (machine, medium host), which is deliberately not ephemeral: the marker is what makes an absent ledger cheap, so it cannot itself be free to lose. Each **ledger** is disposable in exactly two states — before it has ever been held on a host whose barrier is paid, and after the longest window has elapsed with no writer active. Between them it holds spend the platform still counts, and deleting it is a reset that hands the next writer a fresh allowance. The **marker** is disposable in neither; deleting it deliberately is the sanctioned act that precedes a downgrade (prd:self-drive-wake §5.4). The marker is **contractual data, not a sentinel file** (AP-6): a closed, schema-versioned record whose validity predicate is explicit — it is *valid* only if it parses, its schema version is one this build knows, and its host field matches the host it was found under. **Anything else — absent, unparseable, truncated, or a version this build does not know — is treated as absent**, which arms the barrier; a marker is never given the benefit of the doubt, because the whole point of reading it is to decide whether a full window may be skipped. Its **invalidation is durable and is a deletion, not a flag**: the file is removed and the containing directory fsynced before the act is considered complete, so a downgrade cannot leave a marker that survives a power loss and silently exempts the re-upgrade from its barrier.
- **DINV-8** — Every deferral is observable at the moment it is decided: the throttle event carries the **projected** wait and the window's reset deadline, never elapsed time alone. A wait the operator cannot distinguish from a hang is a defect, not quiet (AP-5; incident:I7).
- **DINV-9** — A coarser bound **contains** the finer ones; it never stands beside them. Every content write charges its identity ledger **and** the host umbrella; a write whose identity cannot be resolved charges the umbrella **alone** and never receives a ledger of its own. So no set of processes writing as one identity holds more than one window between them, whatever any of them managed to resolve. A ledger that is merely *keyed* more coarsely, without being charged by the buckets it is supposed to bound, is a second full window wearing the word "coarser" (prd:self-drive-wake/FR-14).
- **DINV-10** — The deferral event's queue depth is the number of callers waiting on **that ledger within the reporting process**, and it names which ledger blocked. It is not machine-wide: the flock coordinates spend, not intent, and a durable registry of intent would be shared mutable state whose staleness after a crash costs more than the number is worth. Every production call site acquires a single write, so reporting the request size would pin the number at 1 however deep the queue grew (prd:self-drive-wake/EVT-4).
- **DINV-11** — **Capacity admission is one atomic decision over every window the write charges.** A **resolved** identity charges two: both locks held in a canonical order, both windows read and tested against one `now`, and the decision to admit is taken for both together or for neither. An **unresolved** identity has no identity ledger (DINV-9), so it charges one — the umbrella's lock, window and decision alone: the whole of that writer's admission, not a degraded variant. The invariant is *atomic over the set a write charges*, never *always two*; a protocol requiring two ledgers cannot execute the unresolved path this design defines. Nothing is charged while waiting: a caller blocked by any window records nothing in any ledger before releasing. **This is a statement about the capacity decision, not about bytes on disk** — what survives a failure mid-commit is DINV-12's, and the two must not be read as one promise. **Initialization is not admission and is excluded from this invariant**: paying a host's cutover barrier is a separate ordered transaction that *must* persist the conservative ledger and the marker before any caller waits (DINV-6, DINV-13), and a caller cancelled during that wait leaves that state behind by design — the barrier is the host's, not the caller's, and it would be re-paid by the next process otherwise.
- **DINV-12** — **Persistence is crash-consistent against host and power loss, and is deliberately weaker than admission's atomicity**: two files cannot be replaced in one step, so a partial outcome is reachable and its *direction* is what this invariant fixes. Each record is replaced by write-to-temp → **fsync the temp** → rename over the target → **fsync the containing directory**, and the next record of an ordered pair does not begin until the previous one's directory sync returns. Two ordered pairs exist, both asymmetric in the safe direction. On the **write path** the umbrella is durable before the identity ledger, so the reachable outcomes are *neither*, *umbrella-only*, or *both* — **identity-only is unreachable**, because it would leave a write charged to no host bound. On **initialization** the conservative ledger is durable before the marker, so the reachable outcomes are *neither*, *ledger-only*, or *both* — **marker-only is unreachable**, because it would report a barrier that was not paid. **Umbrella-only is reachable by ordinary failure, not only by crash** — an fsync or rename error on the identity ledger produces it — and its handling is bound: the caller returns the substrate error, **sends no content write**, and the umbrella's charge is **retained, not rolled back**. Retaining it over-throttles the host by at most `n` and drains on the clock; rolling it back would require a second durable step that can itself fail, trading a bounded over-charge for an unbounded under-charge. Ordering call sites is not ordering durability: an unsynced rename can reach disk after a later one, so a test that kills a process between two writes evidences call order and nothing about power loss.
- **DINV-13** — A **version change in either direction is a gated cutover**, because a build that charges the umbrella and one that does not cannot meter each other's spend. Upgrading: every earlier-build writer is quiesced, then the first initialization of a host's pair pays a **conservative barrier** recorded by the marker. Downgrading: writers stop, the marker is durably invalidated, and no legacy write occurs until that host's **drain deadline** — computed from confirmed quiescence by state class (readable-with-live-entries ⇒ the latest applicable expiry; readable-and-empty ⇒ no wait; missing or unreadable ⇒ the full longest platform window). Neither direction is enforceable from inside either build — they share no state, lock, or vocabulary — so both are **operator preconditions**, and prd:self-drive-wake/UB-8 places the obligation on the documented procedure with **prd:self-drive-wake §6.6's Cutover record and §6.4's launch gate as the enforcing artifacts**. This design implements the barrier half and the marker semantics the drain depends on (A-15, A-17). It does **not** serve prd:self-drive-wake/UB-8 or DOD-10 and does not list them in `Serves`: their acceptance — the drain arithmetic, the corrupt/missing-umbrella variant, the legacy-spend round trip, the breach fixture and the §6.6 compliance evidence — is owned by the operator procedure and the release gate, and a design whose acceptance rows cover none of that would make an unowned obligation read as covered to the stage-6 join. The anchors are cited here, where the dependency is real, and claimed nowhere.

### 3.4 Observability

- **Events/logs** — the reader and budget accept an injected event hook (`func(Event)`, nil = silent): read completions (medium, batch size, cost points, duration, unknown count), unknown resolutions (typed reason), and **budget deferrals**. A deferral emits `throttle_deferred` with prd:self-drive-wake/EVT-4's typed properties: **which ledger blocked** (identity | host-umbrella), a **queue depth** that is the callers waiting on that ledger inside the reporting process — counted guard-entry to guard-exit and sampled at emission, never the request size, which every production call site sets to 1 (DINV-10) — the **projected** wait, never elapsed, and the window's **reset deadline** (DINV-8). The event is emitted at each deferral decision, so a long wait re-announces itself on every re-evaluation rather than falling silent behind one timer. Consumers wire the hook to their sink — wake-watch-v2 wires it to the local wake-events file (its D-9 surface); sweeps may wire it to their run report. The reader itself owns no file.
- **EVT-4 is served here, and was served nowhere before.** No live design carried `prd:self-drive-wake/EVT-4` in its `Serves`, which is the mechanical reason the event was specified and never emitted: nothing bound anyone to emit it. This document takes it. Two consequences for the implementer, both verifiable rather than inferred: the sink's kind for this event is the requirement's name, `throttle_deferred` — a shipped constant spelling it otherwise is drift from the contract, not a competing authority (wake-watch-v2 §3.4's hyphenated list is descriptive prose, and the requirement's other four kinds already match the shipped constants verbatim); and the sink's closed event schema must gain EVT-4's typed properties as fields, since a closed schema (AP-6) cannot carry them any other way.
- **Metrics** — cost points and durations ride the events; the proof-run report (wake-watch-v2's committed artifact) distills them against basis NFR-1's ≤ 10% budget bound.
- **Alerts** — none of its own; staleness/liveness alarms are the consumer's (wake-watch-v2), fed by these events.
- **Debugging surface** — the status verb renders per-proposal `unknown` reasons verbatim; a `--json` style dump of one raw batch is an implementation affordance of the verb, not this port. A deferral's event is the operator's evidence that a stalled write is throttling and not a hang — the distinction §1 records as having cost an hour.
- **Trace/correlation** — events carry the batch id; the executor's existing trace fields apply where the caller supplies them (AP-5).

### 3.5 Security & privacy

**yes** — matches the header row. The *reads* add nothing: they ride the media's existing authenticated clients, open no listener, and send no content to a new destination. The **write budget** is what makes this section non-empty, on two counts.

**It persists state keyed by an authenticated identity.** The ledgers hold write timestamps only — no repository name, proposal reference, or medium content — the umbrella names no identity at all, and the marker holds only its schema version, host, and the fact of the barrier. But a *login* appears in a path. That login is already local knowledge (the medium's own CLI holds the credential it came from), so this discloses nothing new to a principal who can read the state dir; the exposure is that a path is a place, and places can be guessed. **Decision:** every path component derived from medium-supplied text — **the host as well as the identity** — is encoded as `<readable>-<digest>`, where `<readable>` is the input with each byte outside `[A-Za-z0-9._-]` replaced and then truncated to a fixed budget, and `<digest>` is the **first 16 hex characters (64 bits) of the SHA-256** of the raw bytes, taken **before any sanitizing or truncation**. The readable half is bounded at **32 characters**, so a component is at most 49 characters and every path stays well inside the platform limits.

Sanitize-and-truncate alone is **not injective**, and treating it as safe would be the defect: `a/b` and `a?b` both reduce to `a_b`, any two identities sharing a long prefix collide once truncated, and `.` and `..` survive the allowed-character class untouched — so a "sanitized" component can still name its own parent. The digest is what carries uniqueness — **to a stated probability, not to certainty**, which is the honest claim: a 64-bit digest is truncated, so distinct inputs *can* collide, and asserting they cannot would be false by pigeonhole. What the design binds is that a collision requires a **hash** collision rather than a *sanitizing* collision, and 64 bits puts that beyond reach for the population in question — the identities and hosts one machine writes as, a set numbering in the tens. Structurally, because the atom always ends `-<digest>` it can never equal `.` or `..`, can never be empty, and can never traverse. The readable half is legibility only; nothing depends on it.

A path is never constructed from an unsanitized medium-supplied string, and never from the readable half alone.

**It is a production control, not a cache.** The budget decides whether content writes proceed, so its files are an availability and integrity surface: because unreadable contents start conservative, a principal able to *write* those paths can park every pyxis content write for a full window; because an absent marker arms the barrier and a valid one skips it, a principal able to *delete* the marker **costs** a window, and one able to write a **schema-valid** marker **skips a barrier that was never paid**.

Those two are defended differently, and conflating them would be a real error. Malformed content is handled by the predicate: unparseable, truncated, host-mismatched and unknown-version all read as absent, which arms the barrier — the safe direction. **A well-formed forgery is not**, and cannot be: it satisfies the predicate by construction, which is what a predicate is. The only control against it is **access** — §3.8 binds every record owner-only on both the file and its directory, so the set of principals who can forge a marker is the set already entitled to spend the budget. The predicate defends against corruption; ownership defends against forgery; neither substitutes for the other. Write access to these paths is exactly the set of processes entitled to spend the budget.

The injection posture is unaffected: the reader returns data; it carries no instructions and executes nothing it reads.

### 3.6 The GitHub adapter

**Decision:** One GraphQL query per batch — no REST fallback (design-brainstorm:self-drive-wake-tech-design#D-8) — built from **aliased per-ref lookups**, not a plural connection:

- **Exact lookup, one alias per requested ref**: `p0: pullRequest(number: 17) { … }`, `p1: pullRequest(number: 23) { … }`, … The plural `pullRequests` connection **has no list-of-numbers filter**; asking it for a page and hoping the requested refs are in it returns the most recently *updated* proposals instead, which silently answers about the wrong objects. Aliasing is what makes the read exact, and it keeps the round-trip count constant in N (FR-2) because all N aliases ride one document.
- Per alias: `number · state · merged · mergeCommit { oid }` (the claim + revision id, DINV-3); `commits(last:1) → statusCheckRollup → contexts(first: P)` yielding `CheckRun{name, conclusion, checkSuite{app{id}}}` + `StatusContext{context, state, context}` — per-context, never the rollup's own `state` (DINV-4); the three comment surfaces, each with `createdAt` for cursor filtering.
- **The effective required set is the union of two mechanisms, not branch protection alone.** `baseRef → branchProtectionRule → requiredStatusCheckContexts` is one source; **repository and organization rulesets** are the other, and they *compose* — a ruleset can require a check that branch protection never mentions. Reading only branch protection reports a check as unrequired when a ruleset requires it, which is a **false green** under basis FR-3. Both are read in the same document, and the required set is their union.
- **A required check is a (context, source) pair, not a name.** GitHub permits a requirement to be bound to a specific integration, so a check run with the right name produced by a *different* app does not satisfy it. The adapter carries each observed check's producing app identity alongside its name and matches on the pair; where a requirement names no app, any producer satisfies it. Matching on the name alone lets an unrelated — or attacker-installed — app named the same thing turn a red requirement green.

**Decision (required-set fallback):** where neither branch protection nor any applicable ruleset declares required contexts, every *observed* context must conclude successfully for green — strict in the safe direction; a repo that wants looser green declares protection or a ruleset (the medium's own authority — AP-24).

**Decision (completeness and the round-trip bound):** every connection in the document is a **paginated** connection, and the adapter treats a truncated page as an incomplete read rather than an answer.

- Each nested connection is requested with `pageInfo { hasNextPage endCursor }`. GitHub caps a page at 100, so `first: P` with `P ≤ 100` is a page, never a guarantee.
- When any nested connection reports `hasNextPage`, the batch issues a **continuation wave**: one further document requesting only the overflowing connections, by alias and `after: endCursor`, repeated while any still overflow. Continuations are batched — one wave, not one call per overflowing connection.
- Ordering is pinned so cursors are stable across waves: comment surfaces are read in ascending `createdAt` with the node id as tie-breaker, so two records sharing a timestamp cannot straddle a page boundary in an unstable order.
- **What this means for the bound, stated plainly.** FR-2 requires round trips "bounded by a constant independent of N … *within the medium's page size*". The aliased document satisfies that on the axis the requirement is about: **N proposals cost one document regardless of N**. Continuation waves depend on the deepest single proposal's connection — comments on one busy PR — not on N, and the parenthetical is exactly the scope FR-2 draws around them. So the design honors FR-2, and A-2's "≤ 2 round trips" is the *no-overflow* bound rather than a universal one; the kit asserts both it and the N-independence that FR-2 actually requires.
- A proposal whose read is truncated and whose continuation fails is reported `unknown` with the typed reason, never as a proposal with fewer comments than it has (DINV-1, DINV-2). **Silent truncation is the failure mode this section exists to prevent**, and it is the same swallowed-evidence shape as a 200-with-`errors`.

Errors: any GraphQL `errors` entry or transport failure marks **all affected proposals** unknown with the typed reason — the response is checked for `errors` *before* data extraction (a 200-with-errors carrying `null` fields is the exact shape that swallowed evidence in the predecessor, research §3.2). Rate limits: honor `retry-after` where present; the *next scheduled call* is the retry (no in-adapter retry loops — FR-9's semantics make the cadence the retry).

### 3.7 The Carina adapter

**Decision:** A stdlib mtime/size scan of the local store — no watch dependency (design-brainstorm:self-drive-wake-tech-design#D-7) — reading the same record files local-work-tracker-v2 owns: landing from the record's state fields (the store's accepted/closed markers are the medium's claim; the landed revision id is the record's recorded commit), check state from the store's recorded verdict fields, comments from record notes. The exact field mapping is fixed at implementation against local-work-tracker-v2's fixtures (Q1) — the kit's fixture corpus is the binding artifact, so a store-schema drift fails a test, not a user. Scan cost is ~0 (dozens of local files); the adapter's declared advice (consumed by wake-watch-v2) is the 1 s cadence the basis promises. No budget applies (no platform limits — basis FR-8 scopes the throttle to metered media).

### 3.8 The write budget

**Decision:** A token-bucket ledger **pair** — one per **(medium host, authenticated identity)**, plus one **host umbrella** per medium host that every identity ledger also charges — homed in the **machine's** pyxis state directory, flock-guarded, shared by every pyxis process on the machine, and guarded by a durable **cutover marker** per (machine, medium host) (design-brainstorm:self-drive-wake-tech-design#D-6; prd:self-drive-wake §5.4):

- **The home** — the machine's per-user state directory, never a repository checkout. The root is the convention this repository already ships for machine-level state (`${XDG_STATE_HOME:-$HOME/.local/state}/pyxis/…`, as `cmd/pyxis` homes its journal); all three records take paths beneath it rather than introducing a second state-dir authority (AP-11). A checkout's lifetime is unrelated to the window the platform meters: an ephemeral driver checkout is created and destroyed well inside a single hour-window, so a ledger kept there is not machine-shared however its documentation reads — it is per-workspace state wearing a machine-shared name (incident:I7).
- **The key** — one ledger per (medium host, authenticated identity), covering every repository that identity writes to on that host. The platform publishes the content-write caps but not the entity they are scoped to, and reserves the right to change them without notice; throttle state is therefore never partitioned finer than the platform documents its limit. A per-repository key would let N repositories each spend a full window against what may be one identity's quota. A process, checkout, or repository substitute is never admissible as a key component.
- **The umbrella, and why the coarse ledger cannot be a sibling** — each medium host also has one umbrella ledger, and **every** content write charges it in addition to the writing identity's own (DINV-9). When the identity cannot be resolved — an unauthenticated path, a credential the medium will not resolve to a login, a transient lookup failure — the write charges the **umbrella alone** and is never given a ledger of its own. A host-keyed ledger that only unresolved writers touch stands *beside* the identity ledger rather than bounding it, and since identity lookup is retried rather than memoized, a resolved and an unresolved process coexist routinely and spend two full windows against what may be one quota. Charging the umbrella from every write is what makes "coarser" mean *contains* instead of *beside*.
  <br>The cost, stated rather than hidden: two **different** identities on one host share the umbrella's bound, so one identity's burst delays the other's writes on the same machine. That is over-throttling, which prd:self-drive-wake/UB-7 contracts for; a platform rate-limit trip (M3) is what it does not permit.
- **The marker** — a closed, schema-versioned record beside the umbrella it guards, holding its version, the host it belongs to, and the fact of the barrier; nothing else. Its **validity predicate** is explicit because it decides whether a full window may be skipped: valid only if it parses, its version is one this build knows, and its host field matches the directory it was found under. **Absent, unparseable, truncated, or an unknown version are all treated as absent** — the barrier arms. A marker is never given the benefit of the doubt, and an unknown *future* version is a downgrade in disguise, which is exactly when the barrier is wanted. Its **invalidation is a durable deletion, not a flag**: the file is removed and the containing directory fsynced before the act completes, so a power loss during a downgrade cannot leave a marker that silently exempts the re-upgrade.
- **Ownership** — every record's directory and file are owner-only. This is load-bearing rather than hygienic: because unreadable contents start conservative, any principal able to write these paths can park every pyxis content write for a full window by corrupting one, so write access is exactly the set of processes entitled to spend the budget (§3.5).
- **Windows** — a per-minute and a per-hour window over content-writing requests; the limits are named constants in the adapter sourced from the platform's published secondary caps (the constants file cites the platform doc — the live authority; this document deliberately states no cap numbers, which the platform can change).
- **Acquire — atomic over the set the write charges** (DINV-11), not a fixed pair. `Acquire(ctx, n)` runs before every content-write in the GitHub adapter; it blocks until budget or ctx-cancel and never returns "denied" (backpressure, not errors — basis FR-8).
  <br>**Resolved identity — two windows:** take both locks, always umbrella-then-identity (a canonical order, which is what makes holding two locks deadlock-free); under both, read and prune both ledgers against one `now` and test whether **both** have room for `n`; if both do, commit to both, then release; if either does not, **commit nothing**, compute the wait from whichever blocks, release both, emit the deferral, sleep, retry.
  <br>**Unresolved identity — one window:** the same loop over the umbrella alone. A writer that later resolves simply starts charging its identity ledger too; the umbrella entries it already made keep bounding the host, so the transition needs no reconciliation.
  <br>Charging one ledger and *then* waiting on another would fail twice: a caller cancelled or killed mid-wait leaves spend for a write that never happened (and repeated cancellation saturates the umbrella having admitted nothing), and a wait outliving its own admission lets the write proceed past a window that has rolled over.
  <br>Every duration a ledger computes — including the projected wait to the next refill — is derived from the **same injected clock** that stamps its entries; a wait read from the process clock while entries are stamped from an injected one cannot be tested at window scale and is a defect (§3.9).
- **Locks are sidecars, never the records they guard.** A lock is taken on a dedicated, stable file beside each record (`<record>.lock`), created once and **never replaced**. This is not tidiness: `flock` binds to an *inode*, and the replacement protocol below renames a new inode over the record — so a process holding a lock on the record file itself is holding the **old** inode, and a second process that opens the record after the rename locks the **new** one and proceeds concurrently. The mutual exclusion would silently stop existing at exactly the moment a write commits. Sidecar files are never renamed over, so the inode every process locks is the same one.
- **Scratch files are reaped, not merely abandoned** (AP-12). Each replacement writes a temp beside its target, and a crash between create and rename leaves it behind. Temps carry a fixed prefix and are removed on the success path; in addition, any process that holds a record's lock removes temps beside that record older than the longest window before releasing — bounded, deterministic, and performed under the same exclusion that makes it safe. A resource type without a reaper accumulates husks, which is what AP-12 forbids; this is the reaper, and it ships with the type.
- **Durable ordering, and what happens when a commit fails** (DINV-12) — records are replaced by write-temp → fsync temp → rename → fsync directory, and the second record of an ordered pair does not begin until the first's directory sync returns. Write path: umbrella durable before identity, so identity-only is unreachable. Initialization: conservative ledger durable before the marker, so marker-only is unreachable.
  <br>**Umbrella-only is reachable in ordinary operation, not only by crash.** An fsync or rename error on the identity ledger, after the umbrella is already durable, produces it during a perfectly healthy run — and the handling is bound rather than left to the implementer: **return the substrate error, send no content write, and leave the umbrella's charge in place.** The charge is retained deliberately. Rolling it back would need a second durable write that can fail in exactly the same way, so the choice is between a bounded over-charge (at most `n`, draining on the clock) and an unbounded under-charge; this design takes the bounded one. A crash in the same window has the same shape and the same bound.
- **Recovery** — decided by what the state can hide (DINV-6), gated on the host's marker. **With a valid marker, absent ⇒ start empty**: the first write is granted immediately and **nothing is persisted before the grant** — fabricating a full ledger and writing it out extends one process's mistaken start to every process that later shares it, which is how incident:I7's stall outlived the process that caused it. **Present but unreadable ⇒ start conservative**, and the unusable file is replaced so other processes stop re-reading the corruption. **Marker absent or unreadable ⇒ start conservative regardless of the ledgers** — that is the barrier.
- **The cutover, in both directions** (DINV-13) — a build that charges the umbrella and one that does not cannot meter each other's spend, so every transition between them is gated.
  <br>**Upgrading.** Quiescing every earlier-build writer is a **mandatory operator precondition this design cannot implement or verify**: an old binary writes a ledger this one never consults and takes no lock it holds. Without it the barrier is defeated by ordinary timing — an old writer spending at t=59m leaves that spend counted to t=119m while a barrier begun at t=0 expires at t=60m. The barrier covers what quiescence cannot: spend recorded *before* the writers stopped. The first initialization of a host's pair starts conservative, recorded by the marker under the **host umbrella's lock** in the same critical section, so concurrent initializers serialize and exactly one pays it.
  <br>**Probing is not among the mechanisms.** Any probe for evidence of an earlier build — existence, mtime, anywhere — sees only what is discoverable from the probing process, and is defeated by spend in another or a since-deleted checkout, by a legacy process writing after the probe, and by concurrent initialization. A rule that holds only when the evidence happens to be visible is not a bound.
  <br>The barrier costs one window per (machine, host), once — including on a machine that never ran pyxis, which is precisely the case no sound mechanism distinguishes from one that was writing five minutes ago. That narrows, and prd:self-drive-wake §5.4 explicitly narrows, the promise that a never-held ledger is free: it holds within an already-cut-over host, which is where incident:I7 bit — I7 charged a full window to *every ephemeral checkout, indefinitely*.
  <br>**Downgrading** is the mirror and is **out of this design's scope to enforce** — the enforcing artifacts are prd:self-drive-wake §6.6's Cutover record and the §6.4 launch gate that refuses a release whose rollback rehearsal did not walk it: the marker is durably invalidated and no legacy write occurs until the host's drain deadline. What this design owes it is the marker's semantics — the marker records "the barrier was paid *and nothing that fails to charge the umbrella has written since*", which is why a same-build restart retains it and a revert to a non-charging build must not.
- **Batching stays the cheapest budget** — the review write (comments[] + verdict in one call) remains the adapters' shape for multi-comment writes (basis §2.4's evidence row; enforced by NR-2's suites which run with the budget active).
- **Deferral is announced, not silent** — see §3.4/DINV-8: the projected wait, the blocking ledger and the reset deadline ride the event, at each deferral decision.
- Carina: no budget (§3.7).

### 3.9 Testing strategy

Seams binned per the template's menu: the **Carina adapter** is local-substitutable (a real temp-dir store from local-work-tracker-v2 fixtures — test directly); the **GitHub adapter** is remote-but-owned (the port's production adapter + recorded-response fixtures for every DINV case: rollup-green-context-missing, 200-with-errors, rate-limited, pagination; plus one live smoke inside the proof run — AP-14's deployment-context proof); the **kit** runs the same corpus against both adapters — a new adapter passes the kit or it does not exist (AP-3; basis NFR-5).

The **budget** is in-process with an injected clock **that every one of its computations reads** — entries, pruning, and the projected wait alike — so an hour-scale window is exercised in microseconds and a wait is asserted as a value rather than waited out. The deferral sleep is a seam for the same reason. Its cases:

- **cold start, cut-over host** — valid marker, no ledger: the first write is granted with no delay and nothing is written before the grant;
- **un-cut-over host** — marker absent or unreadable: an absent ledger initializes *conservative*, and the first write waits out the barrier;
- **unreadable ledger** — corrupt bytes and a structurally invalid ledger each start conservative;
- **containment** — a resolved and an unresolved writer on one host contend for one window in both directions;
- **the unresolved path** — a writer with no identity ledger is admitted against the umbrella alone, including as a host's first initializer, and later resolves without reconciliation;
- **atomic admission** — a caller cancelled while deferred leaves no entry in any ledger, and repeated cancellation leaves the umbrella empty;
- **burst drill** — nine tasks' write sets concurrently: zero rate-limit responses, zero drops, queue drains, every deferral carrying its blocking ledger, projected wait and reset deadline, and a reported depth reaching the number of concurrent waiters.

Two rules bind this list rather than decorating it.

**A test's fixture must match the state its acceptance names**, or it certifies the opposite behaviour while reading as coverage (incident:I8). The trap here is concrete and was hit during v3's implementation: a fake clock that advances when a waiter sleeps drains the window for whoever arrives first, so the remaining waiters never queue and a depth assertion passes against a depth of one. Waiters are held inside their deferral until all have arrived.

**A crash test proves what it can observe.** Killing a process between two `write()` calls evidences *call order*; it says nothing about what survives power loss, because an unsynced rename can reach disk after a later one. The two claims are therefore verified differently (A-16): call order by in-process injection, durable order by conformance to the write-temp/fsync/rename/fsync-dir protocol, which no in-process test can establish.

## Principles

- **AP-1 — honored.** The read is a port; media vary behind it; the engine never learns which medium answered.
- **AP-3 — honored.** The conformance kit is the adapter-authoring contract; a new medium passes the kit or does not exist (A-8).
- **AP-5 — honored.** The budget's backpressure is observable by construction: a deferral announces its projected wait and reset deadline (DINV-8, A-10), so a throttled stall is distinguishable from a hang without reading code — the gap incident:I7 records.
- **AP-6 — honored.** Closed typed structs end-to-end; unknown is a typed value; no free-form state. The deferral event carries EVT-4's declared properties as typed fields, not an ad-hoc message.
- **AP-11 — honored.** One per-context check derivation (`Checks` delegates); the medium's branch protection is the single required-set authority (§3.6); **one ledger per metered identity and one umbrella per host** — not one per caller, not one per repository, and not a second coarse ledger standing beside the first (DINV-9); and one state-dir root, read from a single helper rather than re-derived per consumer (§3.8).
- **AP-14 — honored.** The GitHub adapter's proof runs in its deployment context, not only against fixtures: §3.9 pairs the recorded-response suite with one live-API smoke inside the proof run, because a medium client that has only ever met its own fixtures has not been tested against the platform.
- **AP-15 — honored.** Decision-critical reads are exact and fresh — no conditional-read caching, no search indexes; the cadence, not a cache, provides cheapness.
- **AP-16 — honored.** Nothing loops or skips silently: a deferral counts and announces itself at *every* re-evaluation, carrying its projected wait and reset deadline (DINV-8, A-10). The failure this document repairs was the principle's exact inverse — one log line, then an hour of silence behind a single timer (incident:I7) — and a wait an operator cannot distinguish from a hang is the silent skip AP-16 forbids.
- **AP-17 — honored (twice, and scoped both times).** Reads fail to *unknown*, and no destructive or dispatch action may derive from a failure (DINV-2) — positive evidence only. The budget applies the rule where failure carries information and only there: unreadable state may hide spend and fails closed; absent state **on a host whose barrier is paid** can hide nothing and fails open — and absence is uninformative until then, which is what the marker records (DINV-6, DINV-13). Conflating those cases converted a safety rule into a self-inflicted outage (incident:I7), this principle's additive half misread as its destructive one. The second application governs uncertainty about *whose* quota is being spent: a coarser bound is safe only when it contains the finer ones (DINV-9), and a coarse ledger standing beside them fails open on a question where failing open hands out a second window.
- **AP-19 — honored (enabling half).** The reader makes zero calls uninvoked; idle cost belongs to the caller's gate (wake-watch-v2).
- **AP-22 — honored.** Reads are idempotent; the budget's acquire is raceable across processes by construction (flock) — now across every repository under one identity, which is the sharing the contract always claimed.
- **AP-24 — honored.** The required-check set is read from the medium's own branch protection — the governing input stays the platform's human-set configuration; no parallel required-list of ours exists to drift from it (§3.6). The same deference sets the bucket key: the platform's documented limit scope governs, and where it documents none we assume coarser rather than invent finer.
- **AP-26 — honored.** Landing is the medium's claim, marked as such and carrying the revision id; ancestry is the consumer's observation (DINV-3).
- **AP-27 — honored.** The port is a new file; adapters extend internally; no shared surface is edited.
- **AP-28 — honored (scoped).** Raw read events are routine ticks (the rule's own carve-out); the teaching distillation is the committed proof-run report (wake-watch-v2's artifact).
- **RW-3 — honored.** No medium workaround crosses the port: GitHub's query mechanics and Carina's scan both die at the adapter boundary.
- **Deviation:** none.
