## Operations

### op: supersede §5.4 Data

Reason: 002's rollback rule is symmetric in intent but not in effect. It correctly stops a *future* re-upgrade from skipping its barrier, and stops the *current* build from discarding live spend by deleting ledgers — but between those two it leaves the moment of downgrade itself unguarded. The older build meters against its own legacy ledger, which knows nothing of the umbrella's live entries, so it starts from an empty window while the platform is still counting v4's writes. The upgrade direction is protected by a barrier; the downgrade direction needs the same idea run backwards, and 002 supplies only half of it.

The partition rule, restated once for both ledgers: throttle state is **never partitioned finer than the platform documents its limit**, and an undocumented scope is assumed coarser, never narrower. The umbrella is what makes that true in the unresolved case rather than merely asserted — the coarser fallback must *contain* the finer buckets, not sit beside them.

The disposability rule, likewise stated once. **Deletion is in contract in exactly two states** — before the ledger has ever been held on a host whose cutover barrier is already paid, and after the longest window has elapsed with no writer active. Between those, deletion is an operator act outside the contract, and it is the only path by which this design can produce a platform rate-limit response.

**The version-change rule, stated once, in both directions.** A build that charges the umbrella and one that does not cannot meter each other's spend, so *every* transition between them is a cutover with a drain, and the drain always runs on the side that is stopping:

- **Upgrading** to a build that charges the umbrella: quiesce every earlier-build writer, then the first initialization pays the barrier, which drains what they left behind (Migration).
- **Downgrading** to a build that does not: stop every umbrella-charging writer, durably invalidate the cutover marker, **then wait out the drain** before the older build is permitted to write. Without that wait the older build meters from an empty legacy ledger while the platform is still counting the umbrella's writes — the mirror image of the upgrade hazard, and equally capable of a rate-limit trip.
  <br>**The drain is defined per affected medium host, and is defined even when the state cannot be read** — a rule that only works on readable state is not a rule, since a corrupt or deleted umbrella is exactly when an operator reaches for a rollback. Per host, measured from the moment quiescence is *confirmed*:
  <br>— **readable, holding live entries**: the drain ends at the latest applicable expiry those entries imply — the newest entry plus the longest window it falls in.
  <br>— **readable and empty**: no wait; the deadline is confirmed quiescence itself.
  <br>— **umbrella missing, unreadable, or structurally invalid**: the drain is the **full longest platform window**, because the unreadable bytes may encode spend as recent as the moment of quiescence. This is the same fail-closed reading the ledgers already use for unreadable state, applied to the clock instead of the window.
  <br>A machine cutting over several medium hosts drains each on its own clock; the older build may write to a host once *that* host's drain completes, and hosts do not wait on one another.

Neither direction is automatable from inside either build: the two do not share state, a lock, or a vocabulary. Both are operator procedures, and both belong on the launch-readiness record (§6.6's Cutover row) with the time of quiescence and the time the drain completed.

- **Migration** — the ledgers move home, but **the platform does not forget**. An upgrade is not a cold start: writes a previous build recorded through a legacy ledger are still inside the platform's window, and letting the new pair start empty hands the machine a second full allowance.
  <br>**Two mechanisms are needed, and neither substitutes for the other.**
  <br>**(a) Quiescence is mandatory, not advisory.** Every pyxis writer of an earlier build must be stopped *before* the new build is started. This cannot be delegated to any in-build mechanism: an old binary writes to a ledger the new one does not consult and takes no lock the new one holds, so nothing the new build does can coordinate with it. Without quiescence the barrier below is defeated by ordinary timing — an old writer spending at t=59m leaves that spend counted until t=119m, while the barrier expires at t=60m and the new pair begins granting. An upgrade performed without quiescing legacy writers is **out of contract**, and DOD-10 demonstrates the breach rather than certifying it away.
  <br>**(b) A first-initialization barrier**, which covers what quiescence cannot: spend recorded *before* the writers were stopped, still inside the platform's window. The first initialization of a host's ledger pair starts **conservative** — both windows assumed spent, refilling on the clock. It is recorded by the **cutover marker**, one per (machine, medium host), written and read under the **host umbrella's lock** in the same critical section that initializes the pair, so concurrent initializers serialize and exactly one pays it. Every later start reads a present marker and is unaffected.
  <br>**Probing is not among the mechanisms.** Any probe for evidence of an earlier build — existence, mtime, anywhere — sees only what is discoverable from the probing process, and is defeated by spend in another or a since-deleted checkout, by a legacy process writing after the probe, and by concurrent initialization. A rule that holds only when the evidence happens to be visible is not a bound.
  <br>**The cost, and what it supersedes.** The barrier is unconditional per (machine, host), so a machine that has *never* run pyxis also pays one window before its first content write on that host. This deliberately narrows 001's promise that a never-held ledger is free: that promise now holds **within an already-cut-over host**, which is where incident:I7 actually bit — I7's defect was every *ephemeral checkout* re-paying a full window, indefinitely, forever. This charges one window per (machine, host), once, and never again; a fresh machine's first hour is a real regression against I7's repair and is accepted here as the price of a bound that does not depend on discovering what cannot reliably be discovered. Removing even that cost requires distinguishing a clean install from an upgrade at install time — an installer-contract question this amendment does not decide and which is the natural place to revisit it.
  <br>Legacy files are never read, migrated, or counted, and are safe to delete once the longest window has passed, together with the lock and temp files beside them.
- **Parallel-run / cutover** — parallel operation of a build that charges the umbrella and one that does not is **forbidden in both directions**, and the version-change rule above is the whole of the procedure.
- **Rollback** — the factory returns byte-identically to operator-clocked sweeps. Rolling back to a build that still charges the umbrella (a same-generation revert) is the kill-switch case: stop it, leave the ledgers and the marker in place, nothing drains. Rolling back to a build that does **not** charge the umbrella follows the downgrade sequence above — stop, invalidate the marker durably, drain the umbrella's longest window, then write. The ephemeral ledgers may be deleted only under the disposability rule; the marker is deleted *deliberately* here, which is the one sanctioned deletion of durable throttle state and is what re-arms the barrier for the eventual re-upgrade.
- **Decommission** — n/a for v1 (nothing replaces it).
- **Privacy check** — no DPIA trigger: no new personal data, no profiling, no monitoring of people. The umbrella holds write timestamps only and names no identity at all; the marker holds no content beyond the fact of the barrier.
- **Egress** — none new: reads travel over the existing authenticated medium APIs; no content leaves the environment to any new destination (and NG-3 forbids the class permanently).

### op: supersede §6.5 Rollout and reversibility

Reason: the kill switch and the cutover steps describe a downgrade that deletes the marker and stops — the half that protects a future re-upgrade — while saying nothing about the drain that protects the downgrade itself, which is the rule this amendment adds.

- **Flag** — none needed: the wake channel activates only when a consumer registers awaits; absent consumers, the code is inert (FR-5).
- **Kill switch** — stop the drive process (or its wake registration): the factory reverts byte-identically to operator-clocked sweeps. This stops *this* build, so the throttle ledgers **and the cutover marker** are left in place — deleting the marker here re-arms the barrier and costs another window for nothing. **Reverting to an earlier build is a different act**, and it is three steps, not one: stop every umbrella-charging writer, durably delete the marker, **then wait out that host's drain** before the older build writes (§5.4's version-change rule). Deleting the marker alone protects only the eventual re-upgrade; the drain is what protects the downgrade itself, and skipping it lets the older build meter from an empty legacy ledger while the platform is still counting the umbrella's writes. As for the ledgers: they cost nothing idle and expire on their own, and deleting them mid-window is the one act that can trip a platform limit (§5.4).
- **Experiment** — none: single-operator dogfood then release.
- **Cutover/migration steps** — **two, and the first is an operator step that cannot be automated.** (1) Stop every pyxis writer of the earlier build before starting the new one; no in-build mechanism can coordinate with a binary that writes to a ledger this one does not consult and takes no lock it holds (§5.4 Migration (a)). (2) The first initialization of a host's ledger pair is then conservative, recorded by the cutover marker under the host umbrella's lock so concurrent starts serialize. No data copy is required. The only optional manual act is deleting legacy files once their window has passed. **Downgrading is the mirror procedure and equally manual**: stop every umbrella-charging writer, durably invalidate the cutover marker, wait out the drain for each affected host — its umbrella's latest applicable expiry, or the full longest platform window if that umbrella is missing or unreadable — and only then permit the older build to write (§5.4; UB-8).
