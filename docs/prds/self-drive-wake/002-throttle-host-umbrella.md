## Operations

### op: supersede §5.4 Data

Reason: 001 keyed one ledger to (host, identity) and let an unresolvable identity "key by host alone", which cannot be a single ledger — a host-keyed ledger sitting beside the identity ledger is a *sibling* holding an independent full window, so two processes writing as the same identity, one of which could not resolve it, could together exceed the platform cap; the rule's promised direction is only recoverable if the host ledger is an umbrella that every identity ledger also charges.

The partition rule, restated once for both ledgers: throttle state is **never partitioned finer than the platform documents its limit**, and an undocumented scope is assumed coarser, never narrower. The umbrella is what makes that true in the unresolved case rather than merely asserted — the coarser fallback must *contain* the finer buckets, not sit beside them.

The disposability rule, likewise stated once. 001 called the ledger "safe to delete" without qualification, which was already too strong for one ledger and is worse for two: a mid-window deletion discards spend the platform still counts, and for the umbrella it also restores the unresolved writer's private allowance. **Deletion is in contract in exactly two states** — before the ledger has ever been held **on a host whose cutover barrier is already paid**, and after the longest window has elapsed with no writer active. The first clause is narrower than 001's, deliberately: absence is free only once the barrier has been paid for that host, because before then an absent ledger is exactly what an un-cut-over machine looks like. Deleting a ledger on a cut-over host costs nothing and the next start is immediate — which is the property incident:I7 required and this contract keeps. Between those, deletion is an operator act outside the contract, and it is the only path by which this design can produce a platform rate-limit response.

- **Migration** — the ledgers move home, but **the platform does not forget**. An upgrade is not a cold start: writes a previous build recorded through a legacy ledger are still inside the platform's window, and letting the new pair start empty hands the machine a second full allowance.
  <br>**Two mechanisms are needed, and neither substitutes for the other.**
  <br>**(a) Quiescence is mandatory, not advisory.** Every pyxis writer of an earlier build must be stopped *before* the new build is started. This cannot be delegated to any in-build mechanism: an old binary writes to a ledger the new one does not consult and takes no lock the new one holds, so nothing the new build does can coordinate with it. Without quiescence the barrier below is defeated by ordinary timing — an old writer spending at t=59m leaves that spend counted until t=119m, while the barrier expires at t=60m and the new pair begins granting. An upgrade performed without quiescing legacy writers is **out of contract**, and DOD-9 demonstrates the breach rather than certifying it away.
  <br>**(b) A first-initialization barrier**, which covers what quiescence cannot: spend recorded *before* the writers were stopped, still inside the platform's window. The first initialization of a host's ledger pair starts **conservative** — both windows assumed spent, refilling on the clock. It is recorded by the **cutover marker**, one per (machine, medium host), written and read under the **host umbrella's lock** in the same critical section that initializes the pair, so concurrent initializers serialize and exactly one pays it. Every later start reads a present marker and is unaffected.
  <br>**Probing is not among the mechanisms.** Any probe for evidence of an earlier build — existence, mtime, anywhere — sees only what is discoverable from the probing process, and is defeated by spend in another or a since-deleted checkout, by a legacy process writing after the probe, and by concurrent initialization. A rule that holds only when the evidence happens to be visible is not a bound.
  <br>**The cost, and what it supersedes.** The barrier is unconditional per (machine, host), so a machine that has *never* run pyxis also pays one window before its first content write on that host. This deliberately narrows 001's promise that a never-held ledger is free: that promise now holds **within an already-cut-over host**, which is where incident:I7 actually bit — I7's defect was every *ephemeral checkout* re-paying a full window, indefinitely, forever. This charges one window per (machine, host), once, and never again; a fresh machine's first hour is a real regression against I7's repair and is accepted here as the price of a bound that does not depend on discovering what cannot reliably be discovered. Removing even that cost requires distinguishing a clean install from an upgrade at install time — an installer-contract question this amendment does not decide and which is the natural place to revisit it.
  <br>Legacy files are never read, migrated, or counted, and are safe to delete once the longest window has passed, together with the lock and temp files beside them.
- **Parallel-run / cutover** — **parallel operation of an earlier build and this one is forbidden**, and that is the whole of the cutover: the two cannot share a bound, because an earlier build writes a ledger this one never consults and takes no lock it holds. The mandatory procedure is Migration (a) above — stop every earlier-build writer *before* starting this one — followed by the barrier in (b). Manual sweeps under this build keep working unchanged (NR-1); manual sweeps under the *earlier* build are exactly the writers that must be stopped.
- **Rollback** — the factory returns byte-identically to operator-clocked sweeps, and the state above divides in two.
  <br>The **ephemeral ledgers** may be deleted under the same disposability rule that governs them — once the longest window has elapsed with no writer active, or before they were ever held on a cut-over host. Rolling back mid-window and deleting live ledgers is the reset this amendment exists to forbid: reversing a deployment does not make the platform's counter forget, so a rollback that cannot wait leaves them in place, where they cost nothing and expire on their own.
  <br>The **cutover marker is durable, and whether it survives depends on what the rollback rolls back to** — because what the marker actually records is not "a barrier was paid once" but "*and nothing that fails to charge the umbrella has written since*".
  <br>**Stopping and restarting the same build** (the kill switch, §6.5) retains it: every writer in that window charged the umbrella, so the record still holds.
  <br>**Rolling back to a build that does not charge the umbrella** invalidates it, and the marker must be **deleted before that build is allowed to write**. Otherwise the rolled-back binary spends through its legacy ledger, and the eventual re-upgrade reads a retained marker, skips the barrier, and grants a fresh allowance against spend that is still platform-live. Like quiescence, this is an operator step no software here can perform: the new build is not running, and the old one has never heard of the marker. Re-upgrading then follows the full procedure — quiesce, then pay the barrier again.
- **Decommission** — n/a for v1 (nothing replaces it).
- **Privacy check** — no DPIA trigger: no new personal data, no profiling, no monitoring of people. The umbrella holds write timestamps only and names no identity at all.
- **Egress** — none new: reads travel over the existing authenticated medium APIs; no content leaves the environment to any new destination (and NG-3 forbids the class permanently).

### op: supersede §6.5 Rollout and reversibility

Reason: the section declared "rollback data path per §5.4 (delete state, nothing breaks)" and "cutover/migration steps — none", both of which the amended §5.4 now contradicts: deleting live ledgers mid-window is a reset that can trip a platform limit, and the move to machine-level ledgers is a cutover whose safety depends on how the new pair initializes.

- **Flag** — none needed: the wake channel activates only when a consumer registers awaits; absent consumers, the code is inert (FR-5).
- **Kill switch** — stop the drive process (or its wake registration): the factory reverts byte-identically to operator-clocked sweeps. This stops *this* build, so the throttle ledgers **and the cutover marker** are left in place — deleting the marker here re-arms the barrier and costs another window for nothing. **Reverting to an earlier build is a different act**: before a build that does not charge the umbrella is allowed to write, the marker must be deleted (§5.4 Rollback), or the re-upgrade will skip a barrier it needs. As for the ledgers: they cost nothing idle and expire on their own, and deleting them mid-window is the one act that can trip a platform limit (§5.4).
- **Experiment** — none: single-operator dogfood then release.
- **Cutover/migration steps** — **two, and the first is an operator step that cannot be automated.** (1) Stop every pyxis writer of the earlier build before starting the new one; no in-build mechanism can coordinate with a binary that writes to a ledger this one does not consult and takes no lock it holds (§5.4 Migration (a)). (2) The first initialization of a host's ledger pair is then conservative, recorded by the cutover marker under the host umbrella's lock so concurrent starts serialize. No data copy is required. The only optional manual act is deleting legacy files once their window has passed.
