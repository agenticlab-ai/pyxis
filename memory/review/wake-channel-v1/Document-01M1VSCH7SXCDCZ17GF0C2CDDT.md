### FND-1 — the §3.7 walk omits its most-strained target statement, and ALT-10's within-touch mitigation is uncarried

- **Severity**: blocking (CAL-2)
- **Lens**: upstream-alignment
- **Evidence**: design: "the walk finds none: the behavior design's 'one problem, one session … ended only by close, park, or the runtime itself' stays true (an await-stop *completes the touch*; …)" (§3.7 — the walk's named statements are agent-v1 §3.2's enumeration, the front door, park mechanics, DINV-4, DINV-5) — vs — argus-agent-v1 §2's Decision callout "executed per problem in **one preferred continuous session** (design-brainstorm:argus-tech-design#D-6)" — a binding statement the walk never names, and the one a wake-architected reality (every await-stop a session boundary, resume the routine path) strains hardest — and the record's chosen alternative, design-brainstorm:argus-unattended-drive-tech-design#ALT-10, whose Trade-offs row admits exactly this cost and binds its mitigation: "the continuous-session *preference* now reads against a wake-architected reality (mitigated: the preference was always within-touch — **the design says so explicitly**)". The design nowhere says it: §3.7 gives the touch model but never reconciles the continuous-session preference, so the record's admitted cost stands unmitigated and the walk's completeness claim ("every binding statement … stays true") rests on an unwalked statement. This disputes nothing recorded — D-5's conclusion re-verified sound; the finding is the fed design not carrying the ruling's own required statement.
- **Acceptance condition**: §3.7's walk names argus-agent-v1 §2's "one preferred continuous session" clause and states the within-touch reading explicitly — the preference binds within a touch (a session held as long as the runtime allows), multi-touch reality rides the designed lossless degrade path, so the statement stays true — or records, with reason, why ALT-10's mitigation is not carried.
- **Disposition**: applied — the first arm: §3.7's walk now opens on the strained statement by name — the behavior design's §2 Decision clause ("executed per problem in one preferred continuous session") — and states the within-touch reading in this design's own voice, carrying ALT-10's mitigation verbatim in substance: the preference always binds within a touch (one session, held as long as the runtime allows, never ended or fragmented by the channel; an await-stop is the touch *completing*; the channel only ever *starts* touches), cross-touch continuity was always the resume protocol's designed lossless ground, and a wake-architected reality multiplies touches without shortening any session the runtime would have held — so the statement stays true and the walk's completeness claim rests on walked ground (Argus, decision principal, tier-2; delivery:argus-unattended-drive#E-34)

### FND-3 — the channel's three configuration knobs have no stated home and no stated relations

- **Severity**: advisory (CAL-4)
- **Lens**: feasibility-completeness
- **Evidence**: design: "a scheduled pass on the drive host at the configured interval" (§3.2), "the configured staleness bound" (#DINV-5), "within the configured bound" (A-2) — three knobs (the tick interval, the latency bound it realizes, the staleness bound) — vs — the record's pinned identity "Interval = the configured latency bound" (design-brainstorm:argus-unattended-drive-tech-design#ALT-7), which the design leaves implicit, and the corpus's config-surface practice (the sibling's policy home was explicitly decided; repo-layout owns the closed-parse config surface). - **Acceptance condition**: the design states the knobs' home (the repo config surface, or an explicit per-host/Q1 deferral with reason) and the binding relations — the tick interval realizes the configured latency bound; the staleness bound exceeds the interval.
- **Disposition**: applied — §3.2 now states both: the knobs live as closed-parse keys at the repo's config surface (final keys at implementation; only the host's *scheduler binding* stays per-adapter, Q1's existing deferral) and the binding relations are explicit — the tick interval realizes the configured latency bound (interval = the bound, the record ALT-7's pinned identity now carried in the design's own text) and the staleness bound strictly exceeds the interval, so a staleness alarm can never fire on an await the very next tick would legally serve — A-5's drill semantics unmuddied (Argus, decision principal, tier-2; delivery:argus-unattended-drive#E-34)
