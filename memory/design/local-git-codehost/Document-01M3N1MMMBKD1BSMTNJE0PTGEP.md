### D-1 — Explicit code-host mode and port boundary

**Decision:** Select `local-git` explicitly in the installed repository's code-host binding. Draft lifecycle, lock recorder, implementation proposal, status, and Argus use consumer-side interfaces for proposal listing, publication, review, merge, and lock evidence. The composition root binds the local adapter; the core does not invoke `gh` or assume a PR number. An unconfigured or mismatched remote is refused before a write.

**Serves:** FR-1 · FR-2 · FR-8 · FR-10

The local adapter accepts one configured bare `origin` path per installed repository, verifies it is a Git repository, and uses Git refs and immutable object IDs. Each operation checks that the working repository uses that configured origin; no separate repository-ID ref or origin initialization step is required. A clone of the configured origin can fetch and check the retained proposal, receipt, and landing records. Copying the origin with its refs and objects can copy those records too, so verification reports consistency of the configured origin's records rather than independent repository identity or cross-origin replay protection. The tracker remains Carina. The existing `RunCommand` process port can remain for Git execution but must not be the code-host semantic port. Hosted GitHub and Forgejo adapters continue to satisfy the same lifecycle interface.

### D-2 — Local proposal object

**Decision:** One proposal has a closed, versioned record with kind (`draft` or `implementation`), feature or task identity, branch ref, current head, target ref and its observed full SHA, state, and monotonic event sequence. The target is derived from the workflow's configured mainline for a draft lock or from the approved feature-integration destination for an implementation task, constrained to canonical `refs/heads/…`; a proposal cannot choose a different target or name a Pyxis evidence ref. Its target must already exist on the configured origin. The record is stored in a dedicated Git ref namespace in that origin. Its reviewable content is the pushed branch at the recorded head. Every publication or revision prepares the branch and proposal objects locally, then updates both refs in one `git push --atomic` with explicit expected old OIDs for both refs. A stale writer is refused without leaving a branch/proposal mismatch. The object can be fetched and inspected from a clone of the configured origin without Carina or network access.

**Serves:** FR-2 · FR-3 · FR-9

The first configured-mainline push is a separate bootstrap operation under FR-9. It uses Git's zero old OID and the pinned Pyxis init epoch for its base-free proof; it creates no local draft proposal or review receipt. Draft open and preparation refuse while the configured origin lacks mainline and name that first-push remedy. Afterward proposal targets use the existing mainline or feature-integration SHA. A crash before atomic proposal publication leaves neither branch nor proposal ref advanced; a crash after it is detected by reading the matching pair and supports idempotent recovery. A revision advances the branch and proposal refs atomically and invalidates previous approval. A remote without atomic push support is refused. Abandonment records a terminal event and retains the reviewed-head archive rather than deleting evidence.

### D-3 — Local review receipt bound to one head

**Decision:** A local approval receipt is a versioned record of a declared operator review. It includes protocol version, proposal identity and kind, the current proposal record's full OID and monotonic event sequence, operation (`draft-lock`, `task-merge`, or `feature-final-merge`), branch, exact full head SHA, fully qualified target ref and its existing old full SHA, readiness digest or exact review/evidence ref, OID, and digest where applicable, and a unique request nonce. A draft lock names `refs/heads/<configured mainline branch>`, derived from `cfg.Branch` as in D-2; an implementation proposal names its actual feature-integration or mainline target. The normal Pyxis route refuses a missing receipt, replay for another proposal on the configured origin, moved head, changed proposal record or sequence, changed target ref or SHA, or changed digest. A revision from `H1` to `H2` and back to `H1` still has a new sequence and record OID, so the old `H1` receipt cannot authorize it. The record cannot authenticate who wrote the receipt or independently identify an origin because the operator waived an independent signing key and shares an OS account with the agent.

**Serves:** FR-3 · FR-4 · FR-5 · FR-6 · UB-1 · UB-2

The operator command renders the request and records a receipt after review in a once-only `refs/pyxis/receipts/<proposal>/<nonce>` ref with a zero-old-OID lease. Landing validates the receipt against the pre-landing proposal record and its sequence; the final proposal record pins that reviewed predecessor OID/sequence and embeds the canonical receipt bytes while landing atomically with the target. A clone of the configured origin reads the final proposal ref to recover the complete receipt even after the review worktree is gone, checks those bytes against the pinned digest and origin receipt ref, then checks the derived target ref and Git objects for consistency. It reports approval and repository identity as unauthenticated. Tests exercise a forged target-ref claim, missing or altered receipt refs, and normal-route refusal of inconsistent receipts; inspection confirms that an agent with access to the shared account could forge a consistent receipt and that a copied origin can retain consistent records. The draft remains blocked until the operator reviews its exact prepared head.

**Accepted security boundary:** The AEC bare origin is writable by the same OS account as the agent. The operator selected that arrangement and waived an independent signing key on 2026-09-28. A local hook or file permission under that account cannot enforce mainline protection; the receipt cannot prove human authorship or a copied origin's independent identity. Pyxis must expose these limits in doctor, receipt output, and clone verification.

### D-4 — Draft preparation and lock transaction

**Decision:** Draft open and preparation first resolve the configured origin's mainline ref. If absent, they refuse before writes and name the installed repository's first-mainline-push remedy from D-2. Once mainline exists, preparation retains the existing rebase, deterministic compile, readiness, memory gate, and change report against its pinned SHA. It pushes a prepared branch head and creates a review request for that head. The local lock command re-reads the remote branch and mainline, checks the receipt and all gates, performs the reviewed squash landing, writes a versioned lock record and tag, and confirms the remote mainline contains exactly the reviewed contract bytes. If any observed ref moved, it refuses and requires a new preparation and review. A clone of the configured origin checks receipt consistency, reviewed head, mainline landing, and lock tag, and reports that neither the review actor nor independent repository identity is authenticated.

**Serves:** FR-3 · FR-4 · FR-5 · FR-6 · UB-1 · UB-2 · UB-3 · UB-4

The lock record carries the proposal ID, reviewed head, mainline commit, receipt digest, readiness digest, version, and declared product and engineering reviewer. Declared reviewer names are not identity evidence. The record must not claim a hosted PR number or code-host review ID. The adapter prepares the landing commit, annotated tag, final proposal record **embedding the canonical receipt bytes**, and immutable reviewed-head archive object before publishing any landing ref. It atomically updates mainline, tag, proposal-state, and reviewed-head-archive refs **and deletes the proposal branch** with explicit expected old object IDs for every changed ref. Branch deletion is a real leased update, so a branch move between the final read and the atomic push rejects the entire landing; a no-op branch push is insufficient. A remote without atomic push support is refused. A crash before that push leaves the proposal prepared; a crash after it is recognized by reading the landing refs, archive, final proposal's embedded receipt, and branch absence and checking the receipt and landing bytes. An interrupted or conflicting retry never manufactures a second lock.

### D-5 — Implementation proposals and Argus handoff

**Decision:** The same local proposal and review-receipt mechanism serves `implement-now` code proposals. Agent workers may publish a branch, checks, and review packet. The operator reviews the exact code head **and its actual target ref**, records a receipt, and invokes the local landing command; Argus may present a review request and later observe the result but never calls the merge operation. Under the shared OS account this procedural actor boundary cannot be authenticated. A task proposal normally targets the remote feature-integration branch; a later feature landing may target mainline. The landing operation rechecks the head, checks, target ref, and current review evidence, then atomically updates the target, final proposal state with embedded canonical receipt bytes, reviewed-head archive, and leased proposal-branch deletion. A moved branch or target rejects the whole transaction. Argus journals the proposal and delivery evidence from the local objects and Carina item, rather than a hosted PR URL.

**Serves:** FR-7 · FR-8

For a task proposal with reviewed head `H` and receipt-bound feature-integration base `B`, require `B` to be an ancestor of `H` and the remote target still to equal `B`. Prepare a squash landing commit `L` with parent `B`, tree `tree(H)`, and canonical task/proposal metadata before the atomic push. The push leases the target `B→L` together with final proposal state, reviewed-head archive, and proposal-branch deletion. Afterward verify `parent(L) == B`, `tree(L) == tree(H)`, and `L` is an ancestor of the freshly fetched feature branch before `RecordLanding`. If two parallel roots began at `B` and the first lands as `L1`, the second proposal's `B` lease refuses: it must rebase onto `L1`, produce a new reviewed head, rerun checks and the complete review aggregate, and obtain a new receipt. Its landing `L2` then has parent `L1`, keeping both landed revisions in the feature-branch ancestry. A merge conflict remains on that proposal for reviewed repair; neither force-push nor a stale receipt discards prior task work.

For a task landing, the local adapter exact-reads the existing `ReviewGate` aggregate for that task, proposal, and current head. It requires the complete `satisfied` result, the current exact-revision codegate verdict, and all required green checks; a missing, partial, stale, or invalidated aggregate refuses before any ref update. Before presenting an operator review request, it stores a canonical envelope containing the aggregate bytes and current proposal record OID/sequence in a Git commit object on the configured origin under immutable `refs/pyxis/review-aggregates/<proposal>/<digest>` with a zero-old-OID lease. The digest covers the whole envelope, so restoring an old head after a proposal revision cannot reuse its old review evidence. A pre-existing ref is idempotent only when its object, bytes, and digest match. The request and receipt bind that ref, its full object OID and digest, and the proposal record OID/sequence from D-3. A resumed run fetches the ref and exact-reads the aggregate without the original review worktree; an existing receipt selects one exact evidence ref, while a run without a receipt may issue a fresh request from current evidence. The final proposal record embeds the canonical envelope and pins its ref/OID/digest in the atomic landing transaction; `RecordLanding` verifies those bytes against the retained ref, same reviewed head, target base, landed revision, and feature-branch ancestry before advancing dependents. A missing or inconsistent evidence ref blocks both landing and post-crash progression. This carries `implement-now-routed-execution` §3.5/#DINV-14 and `feature-implementation-drive` §3.6–3.7 into the local landing predicate.

For a final feature landing, the local adapter exact-reads the accepted `candidate-evidence/v1` record and every required scenario result for `(F,M,C,scenario_set_fingerprint)`. Before presenting an operator review request, it publishes a canonical envelope containing that complete evidence record, its required scenario results, and the current proposal record OID/sequence in a Git commit object on the configured origin under immutable `refs/pyxis/candidate-evidence/<proposal>/<digest>` with a zero-old-OID lease. The digest covers the whole envelope, including the exact candidate identity and scenario-set fingerprint; a pre-existing ref is idempotent only if its object, bytes, and digest match. The review packet and receipt bind the feature head `F`, target-main head `M`, candidate `C`, scenario-set fingerprint, and this evidence ref, full object OID, and digest. A resumed run fetches that ref and exact-reads the complete accepted result set without the evidence-producing worktree. The final proposal record embeds the canonical envelope and pins its ref/OID/digest in the atomic landing transaction; both landing and post-crash delivery verification compare the embedded bytes with the retained ref and reject missing or altered evidence.

The adapter verifies the candidate tree and accepted result set, then prepares mainline landing `L` as a child of `M` with `tree(L) == tree(C)` and a retained feature marker `F'` as a child of `F` with the same tree. The local final proposal branch is a distinct ref at `F`, not an alias of the feature branch. It re-reads `F` and `M` immediately before one atomic push that leases mainline `M→L`, feature branch `F→F'`, proposal branch `F→deleted`, and the final proposal/archive refs. Thus movement of either the mainline, feature branch, or proposal branch rejects the entire landing; the feature branch remains reachable and preserves ancestry. After the push it verifies `L` on freshly fetched mainline, the accepted base `M`, `tree(L) == tree(C)`, and the retained candidate evidence. Missing, negative, or stale candidate evidence refuses. This is the local-mode equivalent of the feature drive's current-candidate gate **inside the normal Pyxis route**; under the accepted shared-account origin it cannot prevent a direct Git write outside that route. A scoped feature-implementation-drive amendment and successor design must authorize this reduced enforcement boundary and feature-branch marker before local final delivery is enabled.

A local proposal reference is a typed Git ref identity, not a fabricated URL. The tracker link can display the ref and full head. Status, logs, and metrics distinguish `local-git` from hosted adapters.

### D-6 — Conformance and security tests

**Decision:** Run the same proposal lifecycle conformance suite against hosted and local adapters. The local suite uses real temporary bare origins under the shared-account policy. It covers the separate first configured-mainline push from the pinned init epoch, wrong/missing-epoch first-push refusal, subsequent history-gate refusal, missing-mainline draft open/prepare refusal with the first-push remedy, a configured mainline branch other than `main`, initialized-origin open, round, concurrent branch/proposal publication, stale push, prepare, readiness failure, missing receipt refusal, exact-head receipt, stale receipt refusal, proposal-head ABA (`H1→H2→H1`) with old-receipt refusal, a branch move between final read and landing push, lock, same-origin fresh-clone consistency verification after deleting the review worktree, missing or altered receipt-ref detection against the embedded bytes, reopen, abandonment, implementation proposal to a feature-integration ref, wrong-target refusal, missing/partial/stale task review aggregates, immutable aggregate-ref publication and fresh-clone recovery after the review worktree is deleted, absent/altered aggregate-ref refusal before landing and `RecordLanding`, two parallel-root task proposals on one base in each human-chosen order (second stale target refuses, reviewed rebase yields a squash child of the first landed revision, and both remain ancestors), reviewed task landing, missing/negative/stale final candidate evidence, immutable candidate-evidence-ref publication and fresh-clone recovery after the evidence worktree is deleted, absent/altered candidate-evidence-ref refusal before landing and after a landing crash, a target-main advance during final landing, distinct final proposal and feature refs, and accepted final delivery with candidate-tree and mainline-ancestry proof. It also checks that outputs disclose the unauthenticated approver, lack of independent repository identity, and absent host protection. It records every spawned command and fails if `gh`, Forgejo, or network is used.

**Serves:** FR-1 · FR-2 · FR-3 · FR-4 · FR-5 · FR-6 · FR-7 · FR-8 · FR-9 · FR-10 · UB-1 · UB-2 · UB-3 · UB-4 · NFR-1 · NFR-2 · NFR-3

The installed-repository acceptance fixture uses Carina, Codex-only Argus, local CI, and a local bare origin. It installs a checksum-verified candidate artifact set packed from the intended release source commit and pinned by version plus manifest hash through the local artifact-source override. It exercises the AEC feature flow, then verifies the Git lock record, Carina status, gate results, and phase metrics. Until the operator approves a specific prepared head, the fixture must stop at an approval request and report that stop honestly.

### D-7 — Rollout boundary

**Decision:** The mode is opt-in. Existing installed repositories keep their selected hosted route. `doctor` reports whether the local origin, configured mainline, and proposal refs are ready, names the first-push remedy if mainline is absent, and states the accepted shared-account trust limits. `pyxis exec` continues to verify candidate and final artifacts. Before local task or final feature landing is enabled, the feature-implementation-drive contract needs a scoped PRD amendment to FR-7, FR-22, and NR-5 plus a reviewed successor design. They must state that the operator invokes the local landing command after exact-head review, while Argus only opens and observes proposals; the shared-account route cannot authenticate that actor or prevent direct writes. The successor must also authorize D-5's current review-aggregate and candidate-evidence checks, atomic ref leases, and explicit outside-route limitation. This draft alone does not supersede the merged feature-drive contracts. After those and the scoped feature-draft PRD amendment and successor design land, the implementation merges, and local conformance passes, `pyxis-release pack` and `verify` produce a candidate set from the intended release commit without requiring a release tag. AEC pins that candidate via the local artifact-source override and completes DOD-4. Only then does the operator tag that same commit and publish the **same verified artifact set** as the final versioned release; AEC repins the published source and reruns installation/doctor smoke checks. A changed source commit or artifact hash invalidates the candidate proof and requires another installed run.

**Serves:** FR-1 · FR-10 · NFR-1 · NFR-3

## Principles

- **AP-1, AP-3 — honored:** Code-host semantics are behind the consumer port and the local adapter joins the conformance kit; the core does not depend on GitHub commands.
- **AP-6, AP-11 — honored:** Proposal and receipt schemas are versioned, and local and hosted paths call the same readiness predicate.
- **AP-13, AP-14, AP-26 — honored within the accepted trust boundary:** Landing checks inspect mainline objects and compiled bytes, not a proposal status alone. These checks prove consistency, not human authorship under the shared account.
- **AP-17 — scoped deviation:** The operator accepted a local mode where the shared account can bypass the normal lock path. The normal Pyxis route still refuses missing or stale receipts; host-level prevention is outside this mode.
- **RW-5 — honored:** The existing feature-draft contract's contradictory approval rule is changed only through a reviewed amendment and successor design before this adapter is enabled.

## Requirement problem

**P-1 (trust model):** D-3 cannot claim the existing code-host branch-protection or independent approval-identity guarantees. The operator chose the shared-account origin and waived an external signing key. The route checks record and object consistency, and its output must disclose that these facts can be forged by an agent with the same OS access.

**Contract dependency:** `prd:feature-draft/FR-17`, `FR-46`, and `UB-3` and `design:feature-draft-v1#DINV-4` currently require authenticated human review enforced by the code host. This local-mode design does not silently override them. A scoped PRD amendment and reviewed successor design must land before the local adapter is enabled; the hosted route retains its present identity check. The AEC test report records the operator's exact-head statement separately because the local receipt cannot authenticate it.
