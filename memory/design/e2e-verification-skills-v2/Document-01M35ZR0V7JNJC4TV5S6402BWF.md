## 1. Problem

The predecessor (`design:e2e-verification-skills`, frozen at merge) specified three skills against a document class whose harness part was a prose paragraph. Its e2e-design accordingly "named a fitting harness and mock approach as authored content"; its e2e-review ran two lenses, neither of which judged whether the machine could be built; its e2e-plan emitted per-scenario tasks and a conditional harness task, and nothing stopped those tasks from landing in the ready frontier all at once, against an empty package, each worker inventing scaffolding the others could not reuse.

Amendment 002 rewrites all three jobs. e2e-design must now author a harness slot form or judge that an existing harness fits and cite it; it must restate every scenario in that harness's terms with the one artifact it exclusively owns; it must specify a stand-in where the flow needs human decisions, and declare what each scenario costs. e2e-review gains a third lens whose whole subject is whether the harness section could be built from. e2e-plan gains a conventions task and an exclusive-ownership contract, and a refusal when the doc cannot supply it.

The predecessor cannot absorb this — a merged design is byte-immutable and the only legal repair is whole-document supersession (incident I6). This document is that supersession, carrying forward the still-valid behavior (the reviewer-program reuse, the live-design-set read, the refusals, the no-automatable-surface stop, app-neutrality, the bounded read) and replacing what amendment 002 falsified. The artifact contract it works against was decided first and separately (`design:e2e-verification-artifacts-v2`); the stage-3 reopen grilled and gated the direction (`design-brainstorm:e2e-verification-tech-design-2`, ready-for-design).

## 2. Decision

**Decision:** The e2e authoring line stays **three separate skills** — `/e2e-design`, `/e2e-review`, `/e2e-plan` — each its own command and a single invocation, reusing existing machinery under the hood. Amendment 002 changes what each does, not how many there are:

- **e2e-design** additionally decides, **by its own judgment over the repository**, whether a harness able to drive this feature's primary interface already exists — citing it and stating only this feature's delta if so, otherwise authoring the full slot form — and authors the stand-in, the per-scenario route/cost/cadence and the per-scenario fixture/seams/owned-artifact. An element it genuinely cannot settle becomes a **blocking open item**, never a library name (`design-brainstorm:e2e-verification-tech-design-2#D-4`).
- **e2e-review** runs **three** blind lenses — coverage, anti-gaming, and **buildability**. The buildability lens reads the document **blind**, with no sight of the well-formedness checker's verdict; findings that merely restate what the checker already raised are filtered **after** the lens returns, never suppressed before it reads (`#D-8`).
- **e2e-plan** emits per-scenario tasks plus a **conventions task** and a **harness task**, each emitted only where the repository does not already supply it, with `blocked-by` edges onto whichever were emitted; every scenario task names the one artifact it exclusively owns, and a document that cannot supply that ownership is **refused** (`prd:e2e-verification/FR-25`, `FR-26`, `UB-9`).

The reasoning: the three steps still carry enough e2e-specific structure to warrant their own commands, and every heavy mechanism they need still exists and is proven. What changed is that the design doc now carries a machine, so the skill that writes it must be able to design one, the skill that reviews it must be able to judge one, and the skill that plans it must be able to hand out non-colliding work — three deeper jobs, not three more skills.

## 3. The design

### 3.1 e2e-design — coverage, the harness, the stand-in, cost, and the refusals

**Decision:** e2e-design reads the feature's **PRD requirement rows** (the coverage backbone), its **live technical-design set**, and the **built code**, and authors the `e2e-design/v2` doc. It **refuses and produces nothing** if any input is absent — no PRD or live design → refuse naming the input (`prd:e2e-verification/UB-2`); not-yet-implemented → refuse naming the unlanded work (`UB-1`) — and it **produces nothing and signals the operator to stop the pipeline** when the feature has no meaningfully-automatable e2e surface (`UB-7`).

- **Coverage derivation** (`prd:e2e-verification/FR-3`) — the required-behavior list is anchored to the PRD's requirement rows, topped up by behaviors the live design set's binding elements and the built code reveal; each required behavior maps to ≥ 1 scenario or an explicit routed disposition. No structured definition-of-done is read.
- **Governing-design-set selection** — a feature may legitimately have **several live technical designs** (the sanctioned artifacts-plus-behavior split; this very feature has two). e2e-design reads the **live, non-superseded set** serving the feature, following the generated index's computed liveness, and derives coverage from the whole set. It surfaces or refuses **only on genuine ambiguity** — a superseded design with no clear live successor, or liveness indeterminable — never merely because more than one design is live (`#DINV-2`).

**Decision:** **whether a fitting harness already exists is the skill's own judgment over the repository** — it reads the existing test trees, judges whether any can drive this feature's primary external interface, and cites it by path. There is **no harness registry** and **no path convention**; existence is not a lookup and not a directory test (`design-brainstorm:e2e-verification-tech-design-2#D-4`).

The judgment picks the harness section's form. A fitting harness found → the **reuse form**: cite it, list only this feature's fixtures, fakes and helpers, and re-decide none of its mechanics (`prd:e2e-verification/FR-20`). None found → the **build form**: an answer under every slot of the closed vocabulary (`FR-19`). A registry was rejected because a shared file every feature must keep true is both a contention point (AP-27) and a staleness hazard whose failure mode this repository has already paid for (incident I6); a path rule was rejected because a directory existing is not a harness that fits — and it would bake a repository layout into skill code against app-neutrality (`NFR-1`).

- **The decision-authority stand-in** (`prd:e2e-verification/FR-22`) — where the flow the tests exercise requires human decisions, e2e-design fills the conditional stand-in slot with all five properties: a scripted answer set consulted first; a persona fallback bound to a written character sheet; every fallback answer recorded as an improvisation, with the assertions depending on it reported non-authoritative; at least one adversarial persona (silence, contradiction, or refusal); and no visibility of the run's assertions to the stand-in. Where the flow needs no human decision, the slot carries a stated not-needed reason. **Specifying** the stand-in is this feature's job; building or running it is the deferred follow-on (`NG-1`, `WR-1`).
- **Scenario normalization** (`prd:e2e-verification/FR-21`) — once the harness section is settled, every scenario is restated in that harness's own terms: the fixture it requires, the seam or seams it exercises (each named in the harness section), and the **one artifact it exclusively owns** under the harness's scenario contract. This is what makes a scenario buildable by a worker and assignable by a planner.
- **Declared cost** (`prd:e2e-verification/FR-23`, `NFR-5`) — every scenario declares one cost class and one cadence alongside its route, and the harness's `cost-controls` slot states the per-run bound in tokens and session count, so one scheduled run's cost is derivable from the document alone.
- **Unsettleable elements** (`prd:e2e-verification/UB-8`) — where no existing harness fits and a slot genuinely cannot be settled, e2e-design records it as a **blocking open item** naming what is unresolved and why. It never lets a library or tool name stand in for missing mechanics, and the document is held short of approval until the element is settled or the dependent scenarios are re-routed (`#DINV-8`).
- **App-shape neutrality** (`prd:e2e-verification/NFR-1`) — the skill reasons about the feature's primary external interface and expresses every shape-specific choice as **authored content in the slots**, carrying no app-shape-specific code (`#DINV-9`). An unroutable *individual* behavior in a feature that otherwise has an automatable surface is surfaced as an open item, never dropped (`UB-3`).
- **Bounded read** (`prd:e2e-verification/NFR-3`) — e2e-design reads a bounded slice (the feature's changed files plus the modules the design set names), never the whole tree; the cap is enforced — a run reaching it stops — with the number tuned at implementation (§7 Q1).

### 3.2 e2e-review — three blind lenses, and the independence wiring

**Decision:** e2e-review stands up as the **fourth instance of the reviewer program**, reusing `context-pack-v1`'s machinery via a stage declaration that maps the e2e design doc onto the admitted **frozen-subject** kind and the feature's PRD + live design set onto **governing-peer** kinds — all existing admitted kinds, no enum change — and reusing the sibling-session **blind fresh-context lens** runtime and scope-locked two-round convergence, emitting an `e2e-review-report/v2`.

- **The three lenses** (`prd:e2e-verification/FR-24`) — **coverage** (every required behavior has a genuine scenario; flags a missing scenario and one obviously unrelated to a behavior it is mapped to); **anti-gaming** (flags a mock strategy that guts the scenario it names, visible because the route and mock are recorded); **buildability** (the harness section answers every slot it owes *with mechanics a worker could build from*, and every scenario is buildable against the harness as specified — its fixture obtainable, its seams carried by the harness, its owned artifact real). Lenses live as **data** — a calibration table plus the lens prompts — so adding or tuning one touches no other lens (`NFR-4`, `#DINV-5`).

**Decision:** the buildability lens reads the document **blind** — it is never handed the well-formedness checker's verdict, or any other lens's. Findings that restate a defect the checker already raised are **filtered after the lens returns**, before the operator sees the report (`design-brainstorm:e2e-verification-tech-design-2#D-8`).

Two reasons, and the order matters. Handing a lens another judge's verdict breaks the reviewer program's standing independence property — its context pack is input-only over admitted kinds and admits no verdict or authoring-trail kind (`#DINV-4`) — and a lens told "structure is already green" is a lens with its scrutiny pre-lowered on exactly the section it exists to scrutinize. Filtering downstream keeps the blindness intact while removing the duplicate noise a zero-tolerance false-red guardrail would otherwise make the operator disposition one finding at a time.

- **The genuine-exercise boundary** (`prd:e2e-verification/ABUSE-4`) — there is still **no design-time mechanism** for verifying a coverage-map edge is genuinely exercised: whether a built test fails when the code breaks can only be confirmed by running it against broken code, which the basis defers to the build follow-on (`WR-1`). Design time catches gross over-mapping, self-contradicting mock plans, and — new here — a harness nobody could build from.
- **Blocking / advisory convergence** (`prd:e2e-verification/FR-10`, `UB-5`) — each finding carries a severity and an acceptance condition; the loop runs until every finding is **settled** — a blocking finding solved in the design or explicitly rejected with a stated reason, an advisory one resolved or rejected — and no design with an open finding advances to e2e-plan (`#DINV-10`).
- **The human half** (`prd:e2e-verification/FR-9`) — the operator's comments on the design document in conversation run **alongside** the unmanned lenses, both feeding one convergence loop.
- **Reviewer-level authority** — the reviewer is **advisory in v1**: it forces no downstream automated gate, because none exists and the operator is the approval point. That authority graduates like the other reviewers once a build or gate enforcement surface exists (§7 Q3); the model-driven catch corpus **measures**, never gates (I5).

### 3.3 e2e-plan — conventions before fan-out, and exclusive ownership

**Decision:** e2e-plan authors an ordinary plan-new **`plan/v1`** from the **approved** e2e design doc, carrying three task kinds:

| Task | Emitted when | Edges |
|---|---|---|
| **harness task** | the feature's e2e harness does not already exist | — |
| **conventions task** — lands the harness's scenario contract and one worked scenario | the repository does not already carry a scenario built against that harness | `blocked-by` the harness task, where one was emitted |
| **scenario task** — one per scenario | always | `blocked-by` each of the harness and conventions tasks that were emitted; none where the repository supplies both |

Every scenario task **names the one artifact it exclusively owns**, taken from that scenario's build-facts row, and **no two scenario tasks in a plan name the same artifact** (`prd:e2e-verification/FR-26`, `#DINV-7`).

The conventions task is the answer to a failure the predecessor's plan shape produced structurally: scenario tasks blocked only on the harness still entered the ready frontier simultaneously, against a package with no landed example, so each worker invented its own scaffolding in the same place and collisions were guaranteed rather than unlucky. Landing the scenario contract and one worked scenario first gives every parallel worker a shape to copy. Both it and the harness task are conditional because a repository that already supplies either does not need it rebuilt.

**Decision:** e2e-plan **refuses** on an e2e design doc that is not operator-approved (`prd:e2e-verification/UB-4`), and **refuses** on an approved doc whose scenarios do not each name one exclusively-owned artifact — naming the offending scenarios and projecting zero tasks (`UB-9`, `#DINV-7`). Ownership is a property the design must supply and the review must have seen; a planner that invented it would be assigning work the review never checked, and would own the resulting collisions itself.

The declared edges are all that is needed: the executor's existing **ready frontier** (open ∧ unblocked ∧ unclaimed) orders harness → conventions → scenarios for free and never bases a task on an unmerged blocker. Because the plan is an ordinary plan-new `plan/v1`, freeze-at-merge, idempotent projection and the task/charter schema are reused verbatim, and **this feature edits implement-now not at all** (`prd:e2e-verification/FR-14`, `NR-1`, `NR-2`, `#DINV-6`).

### 3.4 Skill separation, single invocation, and who runs the checker

**Decision:** each of the three skills is its **own user-facing command and a single invocation**; every reuse of existing machinery is **internal** — the operator never separately invokes a reused skill or tool. One `/e2e-design`, one `/e2e-review`, one `/e2e-plan` call each does that skill's whole job.

**Decision:** the artifact class's well-formedness **checker is invoked by these skills** — e2e-design runs it over the document it has authored **before emitting it**, refusing to emit a malformed doc, and e2e-review runs it over the subject **at the start of a review round**. On a malformed subject e2e-review **refuses the round**, returning the checker's defects instead of running the lenses, so no review round is spent on a structural defect and no lens output is produced against a document that should not have been submitted. The checker's *rules* are the artifact contract's (`design:e2e-verification-artifacts-v2` §3.5); only the invocation and this refusal branch are behavior, and they live here because a checker nothing calls — or whose verdict nothing acts on — would leave that contract's integrity claim resting on a component with no consequence (`#DINV-12`).

### 3.5 Boundaries and non-goals

- **Not solved here** — the artifact schemas, the slot vocabulary, the checker's rule set, the home and the lifecycle (`design:e2e-verification-artifacts-v2`).
- **Owned by a future design / feature** — building or running the tests, run-time anti-gaming, and any proof that a built scenario bites (`prd:e2e-verification/WR-1`); the feature-evolution / e2e-test-delta capability; the reviewer's downstream-gate authority (§7 Q3).
- **Owned by `prd:implement-now`, not this feature** — the executor's e2e-task briefing reads the e2e design doc to brief a worker, and was built against the class this pair of designs replaces. Adapting it to `e2e-design/v2` is implement-now's own change, made under its own ledger; **this feature edits no implement-now contract or code** (`prd:e2e-verification/NR-2`), which is exactly why the adaptation cannot be smuggled in here. Named so it is not discovered later (R6).
- **Two stranded lineage edges, named and left standing** — retiring this document's supersession target flags every live design that builds on it. Two do: **`impl-review-routed-assurance`**, which carried no staleness flag before this change and now carries `stale-builds-on`, and **`implement-now-e2e-tasks`**, which gains a second stale edge. Both are merged, and re-pointing a merged design's lineage row is not legal — `check-immutable` refuses any edit to a merged design, and incident **I6** cost this repository a mid-repair reversal on exactly that attempt, leaving whole-document supersession as the only lawful repair. Each flag therefore **stands until its own design is superseded**, under `prd:impl-review` and `prd:implement-now` respectively — neither this feature's to edit (`prd:e2e-verification/NR-1`, `NR-2`). Named here because I6's lesson is that such a flag is a planning blocker in waiting, never decoration.
- **Implementation must not infer** — that e2e-review edits the reviewed doc (it raises findings; the author or operator resolves them); that a lens sees the checker's verdict or another lens's findings (it does not — filtering happens after, §3.2); that the reused context pack shares judgment (input-only, finding-blind, no authoring-trail kind); that the executor or plan-new is changed (`#DINV-6`); that a blocking finding is un-rejectable (it must be **settled**, never left open); that the no-automatable-surface case yields any artifact (it produces nothing and stops — `#DINV-3`); that a harness registry or path convention exists (neither does — §3.1); that e2e-plan may assign artifact ownership itself (it refuses instead — `#DINV-7`).
- **Must remain unchanged** — the existing pipeline skills and reviewer program (`prd:e2e-verification/NR-1`); implement-now and plan-new's pipeline (`NR-2`); the repository's existing required CI contexts (`NR-3`).

### 3.6 Invariants

- **DINV-1** — e2e-design refuses and produces nothing when the PRD, the live technical-design set, or the built code is absent (`prd:e2e-verification/UB-1`, `UB-2`).
- **DINV-2** — e2e-design reads the live, non-superseded design *set* serving a feature; it surfaces or refuses only on a superseded design with no clear live successor or indeterminable liveness — never merely because more than one design is live (`UB-2`).
- **DINV-3** — nothing is silently dropped or fabricated: an unroutable *individual* behavior is surfaced as an open item (`UB-3`), and a feature with **no automatable e2e surface** yields **no e2e documents** and a stop-the-pipeline signal — never a fabricated or manual-only artifact (`UB-7`).
- **DINV-4** — no lens is handed another judge's verdict. The context pack stays input-only over admitted kinds, admitting neither the well-formedness checker's result nor another lens's findings nor the authoring trail; duplicate suppression happens strictly **after** a lens returns (`prd:e2e-verification/FR-7`).
- **DINV-5** — the lens set is data (calibration rows plus prompts); adding or tuning a lens touches no other lens's logic (`prd:e2e-verification/NFR-4`).
- **DINV-6** — the plan is an ordinary plan-new `plan/v1` using the ordinary task and charter schema with no new type; plan-new's pipeline and the executor are consumed unchanged, and this feature edits neither (`prd:e2e-verification/FR-14`, `NR-1`, `NR-2`).
- **DINV-7** — every scenario task names exactly one exclusively-owned artifact and no two name the same one; e2e-plan **refuses** — naming the offending scenarios and projecting zero tasks — on an approved doc that cannot supply that ownership, and never assigns ownership itself (`prd:e2e-verification/FR-26`, `UB-9`).
- **DINV-8** — e2e-design records an unsettleable harness slot as a blocking open item naming what is unresolved and why, and never lets a library or tool name stand in for missing mechanics (`prd:e2e-verification/UB-8`). The mechanical bar is the artifact class's shape floor (`design:e2e-verification-artifacts-v2#3.5`), which e2e-design clears before emitting (#DINV-12); whether an answer that clears it genuinely specifies a machine is the buildability lens's.
- **DINV-9** — e2e-design carries no app-shape-specific code; every app-shape choice is authored content filling the slots, so a new app shape needs no skill-code change (`prd:e2e-verification/NFR-1`).
- **DINV-10** — a blocking finding must be settled (solved in the design, or explicitly rejected with a stated reason) before approval; no design advances to e2e-plan with an open finding (`prd:e2e-verification/FR-10`, `UB-5`). e2e-plan refuses on an unapproved doc (`UB-4`).
- **DINV-11** — e2e-design's bounded read and e2e-review's convergence round cap are enforced: a run reaching either stops rather than fanning out (`prd:e2e-verification/NFR-3`).
- **DINV-12** — e2e-design runs the artifact class's well-formedness checker over its output before emitting and never emits a malformed doc; e2e-review runs it over the subject at the start of a round and **refuses the round on a malformed subject**, returning the checker's defects and running no lens. Neither skill re-implements or overrides a checker rule — the rules are `design:e2e-verification-artifacts-v2` §3.5's (`prd:e2e-verification/FR-18`).

### 3.7 Observability

- **Events/logs** — the skills emit the basis's tracking plan (`prd:e2e-verification/§5.7`): `e2e_line_step`, `review_finding` (whose lens property now admits **buildability**), `catch_corpus_run` (whose case-family property now admits **harness_hole**), and `finding_disposition`; logged via `log/slog` with the run context. A finding removed by the post-hoc duplicate filter is logged as filtered rather than dropped silently, so the filter's reach is measurable (§7 Q4).
- **Metrics** — M1 (a feature carried design → review → plan to an accepted plan) and M2/M3/M4 (the coverage, anti-gaming and buildability catch-rates at the checkpoint), computed from the retained records and surfaced at the checkpoint, never per-commit gates (I5).
- **Alerts** — none intrinsic (invoked skills, no daemon); a stuck review is bounded by the convergence round cap and surfaced as a non-terminating-run signal.
- **Debugging surface** — the artifacts are self-describing: the coverage map and the two scenario tables show what was decided, the harness slots show what machine was specified, and the review report's findings and dispositions show what the lenses caught and how each was settled.
- **Trace/correlation** — each skill run carries its invocation context, threading the run to its feature and artifacts.
- **Retained fuel** (AP-28) — the review report and the catch-corpus run record accrete in git as committed, append-only records — the corpus the advisory-to-blocking ramp reads — never only ephemeral logs.

### 3.8 Security & privacy

Matches the header row: **yes**.

1. **Model/provider egress** — e2e-design and e2e-review make model calls carrying the feature's own repository artifacts (PRD, technical designs, code, the design doc under review). This is the **same egress class as every existing authoring and review skill**, with no new destination, and the content is the operand's own repository (`prd:e2e-verification/§5.4`).
2. **No standing access surface** — the skills are operator-invoked, hold no roles or credentials, and their outputs (design doc, review report, plan, tracker tasks) are human-reviewed content (`§5.3`).
3. **Review independence** — the lenses are blind over an **input-only** context pack admitting no verdict, no other lens's findings, and no authoring-trail kind, so a lens is never handed an answer key (`#DINV-4`). The post-hoc duplicate filter is deliberately outside that boundary: it reads lens output, never feeds lens input.
4. **The stand-in as an adversarial surface** (`prd:e2e-verification/ABUSE-5`) — a decision-authority stand-in specified as cooperative-only, assertion-sighted, or silently improvising would manufacture a green on any agentic feature. The five properties of `FR-22` are the mitigation and the buildability lens is what checks they are real (§3.1, A-4).

No personal data; no secrets. Mitigations trace to `#DINV-4`, `#DINV-8`, and A-3/A-4.

## 4. Alternatives considered

| Alternative | Why rejected |
|---|---|
| **A harness registry** — a declared file naming each harness, its app shape, its path and its specifying document (`design-brainstorm:e2e-verification-tech-design-2#ALT-5`) | turns existence into a same-answer-every-run lookup and is the only shape in which a fork between two features citing one harness is detectable — but it is a shared file every feature must keep true (AP-27 contention), and a stale shared index is a planning blocker in waiting, a failure mode this repository already paid for (I6). Nothing in the current contract asks for it |
| **A path convention** — a harness is whatever lives at a fixed path for the feature's area (`#ALT-6`) | zero new surface and fully mechanical, but it answers the wrong question: a directory existing is not a harness that can drive this feature's interface, so a fitting harness in another area's tree is invisible and gets rebuilt. It also bakes a repository layout into skill code, against `NFR-1` |
| **Hand the buildability lens the checker's verdict** so it skips structural checking | breaks the reviewer program's independence property — the pack is input-only and admits no verdict kind — and pre-lowers the lens's scrutiny on the very section it exists to scrutinize. Post-hoc filtering gets the same clean report without touching the boundary |
| **Suppress duplicate findings by narrowing the lens prompt** instead of filtering after | the same defect wearing a different hat: telling the lens "do not look at structure" is telling it what the checker found, indirectly |
| **Always emit the conventions and harness tasks** | rebuilds what a repository already supplies; both are conditional on what is actually there (`prd:e2e-verification/FR-25`) |
| **No conventions task — scenario tasks blocked only on the harness** (the predecessor's shape) | leaves every scenario task in the ready frontier at once against an empty package, so parallel workers each invent scaffolding nobody reuses and collide on shared files — structurally, not by bad luck |
| **Let e2e-plan assign artifact ownership** when the design doc does not | the planner would invent an assignment no reviewer checked, and would own the resulting collisions; refusing pushes the fix back to the artifact where the review can see it (`UB-9`) |
| **A parallel e2e-specific reviewer** not reusing the reviewer program *(carried forward)* | re-invents proven machinery — context pack, blind lenses, convergence, the report family — and its independence guarantees; the basis mandates adopting the existing shapes (`FR-7`) |
| **App-shape-specific skill code** *(carried forward)* | ties the skills to an enumerated shape set and needs code per new shape; carrying shape choices as authored content in the slots keeps them app-neutral by construction (`NFR-1`) |
| **A dedicated design-time genuine-exercise check** *(carried forward)* | genuine exercise can only be confirmed by running the built test against broken code, deferred to `WR-1`; a design-time version would be theatrical |
| **One combined e2e skill**, or a multi-step invocation chain *(carried forward)* | blurs the user-facing boundary and the reuse-under-the-hood property; each step is a distinct command with a single invocation |

## 5. Risks

| ID | Risk | Impact | Mitigation | Verification / evidence |
|---|---|---|---|---|

| R4 | Auto-authored coverage stays shallow — thin scenarios, missed behaviors | end-to-end gaps ship unproven | coverage anchored to the PRD requirement rows (`FR-3`) plus the coverage lens plus the human review; the explicit coverage map is the yardstick, and the dogfood measures it | A-1, A-4; the dogfood (M1) |
| R5 | The stand-in is specified to pass rather than to probe — cooperative-only, assertion-sighted, or silently improvising (`ABUSE-5`) | an agentic feature is driven to green by the answers that make it green | the five properties of `FR-22` are mandatory slot content and the buildability lens checks them, with cooperative-only and assertion-sighted cases seeded in the corpus | A-4 |
| R6 | The executor's e2e briefing breaks — it reads the e2e design doc and was built against the class this pair replaces | e2e tasks brief workers from a document shape that no longer exists | named as out of scope and owned by `prd:implement-now` (§3.5); this feature edits nothing there, so the break is visible at that feature's own gate rather than silently absorbed here | §3.5; A-7 (this feature's diff touches no implement-now surface) |
| R7 | Over-mocking hollows the suite — subtle cases invisible at design time *(carried forward)* | a routed-looking suite exercising little | routes recorded per scenario and reviewed (`FR-4`) plus the anti-gaming paper check; the deep bite-check is the deferred run-time falsification (`WR-1`) | A-4; dogfood review |

## Principles

- **AP-10 / AP-21 — honored.** Mechanical parts are codified or reused (the class's checker, the plan's `blocked-by` ordering, the projection); judgment — coverage, harness existence, lens verdicts — is placed once at the skill and frozen into the artifact the downstream reads verbatim.
- **AP-11 — honored.** One reviewer program (a fourth instance), one context-pack machinery, one plan pipeline, one executor frontier — reused, not twinned. The rejected harness registry would have added a second lookup surface for a question the skill can answer.
- **AP-13 / AP-14 — honored.** The review's teeth are on the artifact (blocking findings settled before approval, ownership refused rather than invented); acceptance of a test's genuine bite is **not** claimed at design time — it is the deferred run-time check (`WR-1`).
- **AP-19 — honored.** Bounded per-run cost: the bounded code read and the convergence round cap (`NFR-3`), both enforced; and the skills now make the *authored suite's* cost a declared property too (`NFR-5`).
- **AP-5 — honored.** The skills emit the basis's event plan, with the lens and case-family enums widened for the third lens, and the artifacts are self-describing.
- **AP-25 — honored.** The skills are vendor-neutral authoring surfaces, app-neutral by construction (`NFR-1`, `#DINV-9`); no app shape and no repository layout is encoded in skill code.
- **AP-23 — honored.** The principle §3.3 is a direct instance of, in its own three clauses: work decomposition **declares the files each task touches** (every scenario task names the one artifact it exclusively owns, no two the same — `FR-26`, `#DINV-7`); it **sequences the overlaps** (the `blocked-by` edges onto the emitted conventions and harness tasks); and it removes the conflict magnet **structurally** rather than by a recovery loop (the conventions task lands the scenario contract and one worked scenario *before* the fan-out, so parallel workers copy a shape instead of each inventing one in the same package).
- **AP-27 — honored.** No shared append surface is introduced: the harness registry was rejected partly on this ground, and every artifact stays per-feature.
- **AP-28 — honored.** The improvement-fuel outputs — the review report's findings and dispositions, the catch-corpus run record, and the duplicate-filter log — are retained as committed, append-only git records.
- **NR-1 / NR-2 — honored.** Additive: the existing skills, reviewer program, plan-new pipeline and executor are byte-unchanged by this feature. Where the executor's own e2e briefing must later adapt to the new class, that change belongs to `prd:implement-now` and is named as such (§3.5) rather than taken here.
- **RW-5 — honored.** One decision — the three skills' behavior; the artifact contract they produce and consume is the separate, independently-revisable `design:e2e-verification-artifacts-v2`.
- **I5 — honored (incident lesson).** Model-driven verdicts measure and never gate: the catch corpus scores the lenses at a checkpoint rather than per commit, and the structural half of harness integrity is a hermetic checker's job, not a lens's.
- **I6 — honored (incident lesson).** The frozen predecessor is evolved by whole-document supersession, never by editing its lineage rows.
- **Deviation:** none.
